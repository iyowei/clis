## 校验不变量

任一删除目标必须同时满足以下条件, 否则整批拒绝 (保守优先):

1. 路径的最后一段恰好是 `node_modules` (对原始输入和 realpath 两种形态都要判);
2. realpath 之后必须位于某个 `roots` 之下 (以 path.relative 语义判定, 禁止用字符串前缀比较; win32 下不区分大小写);
3. 不能是 `/` 本身, 也不能是家目录本体;
4. realpath 去重后不能有重复目标;
5. **根锚点链**: 配置里的根 (按原始拼写) 及其祖先链 (从文件系统根下面第一级开始, 一直到配置里的根自身; 文件系统根 `/` 本身不入链, 它不可能是符号链接), 逐级都必须是真目录 (用 lstat 判定, 不跟进末段); 任何一级是符号链接 → 该根下的目标全部拒收 (整批拒绝)。系统自带的链接 (macOS 的 `/tmp`、`/var`) 同样会命中, 改写成真实路径的形态就放行; 根不可解析 (realpath 失败) 时, 该根下没有归属目标, 不牵连其他根。同一套判定也服务于 `init` 的落盘目标 (写入侧对配置路径的锚点检查, 看的是「链接会让写入改写它指向的目标」), 见 [行为契约](../protocol/behavior-contract.md) BC-40。

**为什么第 5 条看拼写, 而不是 realpath**: 拿 `realpath(root)` 去验根, 等于自己证明自己: 不管配置里的名字被换成什么, 它只会报告「此刻解析出来的结果」, 「名字 → 真实路径」这个映射有没有被改动过, 它根本显示不出来; 而第 2 条和删除层复核链比较时两侧都取 realpath, 根一旦被替换, 两边就一起跟着变, 比较永远成立。于是攻击者只要做一次手脚 (不需要竞态, 布置一次就持久生效, 离线也能完成): 把根改名搬走, 原地放一个符号链接指向别的目录树, 此后每次 `--yes` 都会把删除导向那棵树, 而报告上写的是「成功」。唯一能识破这件事的证据, 就是拼写形态。

**与 BC-11 的分工 (扫描会跟进链接, 删除不放行)**: [扫描算法](scan-and-size.md) 里「根自身为符号链接 → 照常扫描 (显式即授权)」说的是**扫描侧** (预览零副作用, 跟进链接没有风险); 本节第 5 条说的是**删除侧的信任锚**。同一个场景下两者同时成立: 预览照常出清单, `--yes` 时整批拒绝; 删掉的东西装不回来, 删除侧的门槛就是要比扫描侧高, 两者不冲突。

## 语义闸: 疑似安装树默认不进删除批

不变量判的是「路径形态与归属是否安全」, 不管「这个 node_modules 是不是用户的项目依赖」。初始化向导的默认根是家目录, 而家目录下的安装树 (包管理器的全局包树、版本管理器的 node 安装、编辑器扩展目录、系统 / 应用数据根) 同样满足这些不变量, 却不符合 ADR 0002 给出的删除前提: 删了没法靠项目级重装恢复 (本机实测 `~/.bun/install/global` 4.25 GB / 1627 包, 而且本工具自己也装在它里面; 版本管理器的 `lib/node_modules` 是用户全局包清单唯一存放的地方)。所以在构造删除批次时, 另加一道语义闸:

- **类别判定** (`classify.ts`, 纯函数, 只看路径形态, 三级依次判定、命中即停): ① `node_modules` 上面任何一级目录的名字命中安装树容器名 (默认排除名单 ∪ `extensions` / `_npx`); ② `node_modules` 的父目录名是 `lib` (fnm / nvm / volta / asdf 的全局包一律装在 `<版本目录>/lib/node_modules`); ③ `node_modules` 在家目录下的隐藏目录里 (应用私有根常常设在这个位置; 实测命中 `~/.oh-my-opencode` 237 MB、`~/.stepfun/releases/deps-6`、`~/.jcode/skills/archify` 等没有收进默认名单的应用根; 这种名字没法穷举, 所以按路径形态兜底)。命中任意一条即判为**疑似安装树**, 其余判为项目依赖。比较时一律忽略大小写 (多出来的误判都落在安全侧); 判定不受用户配置影响 (用户把默认排除项删了, 这道闸也还在);
- **默认行为**: 疑似安装树不进删除批, 在执行报告里按失败侧呈现 (行尾「已跳过 (加 `--force` 一并清理)」, 退出码 1, 和「未测到体积」同属「未处理目标」); 预览里按判定结果给行尾加标记, 并保留路径末尾的 `node_modules` 后缀 (剥掉后缀会把安装树显示成项目);
- **放行通道**: `--force` 显式放行, 疑似安装树照常进入删除批; 这个旗标只影响批次构造, 不放宽安全闸的不变量, 也不改变预览零副作用的语义;
- **误判登记 (保守的代价)**: monorepo 里名为 `lib` 的包 (`packages/lib/node_modules`)、名为 `extensions` 的容器、以及刻意藏在点目录里的项目 (`~/.my-project/node_modules`), 同样会被判为疑似。判定只看路径、不看目录内容 (读内容会让判定和磁盘状态绑在一起: 竞态、权限噪声, 还越过了纯函数的边界); 家目录自己的 `node_modules` 不受影响 (它仍按项目判, 家目录本身也可以就是一个工作区)。误判的代价无非是加一次 `--force`, 偏向安全的一侧; 反过来 (把真正的安装树判成项目) 才是不可逆的损失。

## 设备边界: 跨设备目标默认不进删除批

不变量判的是「路径形态与归属是否安全」, 语义闸判的是「删了能不能靠项目级重装恢复」, 两者都不看目标落在**哪个文件系统**上。根只是路径上的授权范围: 根之下的挂载点 (云盘 / 网络挂载 / 容器卷) 会把另一个文件系统的内容带进这条路径, 于是「根之下的 node_modules」可能在另一块盘、另一台机器上。跨设备删除删的是授权路径之外的实际存储 (远端文件系统的删除往往没有回收站可退, 还可能被同步到别处), 而且删除量和根所在卷释放的量对不上, 所以在构造删除批次时, 另加一道设备边界闸:

- **判定** (`guard.ts` 的 `findCrossDeviceTargets`): 逐条比对目标和它所属根的 `st_dev`; 目标取 `lstat` 语义 (与 `fs.rm` 对末段的语义对齐: 目标是符号链接时只删链接, 不跨设备), 根取 `stat` 语义 (以根解析到的实际目录为准)。归属取**最具体的根** (包含该目标、路径最长的那个): 设备比对需要一个唯一的参照; 而把挂载点声明为独立根, 就是在明确表达「这个卷归我处置」;
- **两种形态分开写** (解除路径不同, 不能合成一句): `on-path` = 挂载点在根和目标之间 (目标与父目录同设备), 解除路径是**把该挂载点声明为独立根** (写进配置 `roots` 或加 `--config`); 声明后该目标归它管、设备比对通过、照常删除。`target-itself` = 目标本体就是挂载点 (目标与父目录不同设备, 卷里的数据不在这个目标的删除范围内), 声明根无济于事, 只能先卸载该卷; 而且即便放行, 挂载点的 `rmdir` 也必然 `EBUSY` (卷不能靠删目录卸掉);
- **默认行为**: 跨设备目标不进删除批; 预览里按形态给行尾加标注 (`跨设备: 根与目标之间有挂载点` / `跨设备: 目标本体即挂载点`), 执行报告按失败侧呈现 (行尾「已跳过 (把该挂载点声明为独立根即可清理)」/「已跳过 (挂载点无法删除, 需先卸载该卷)」), 退出码 1 (和疑似安装树同属「未处理目标」); 在末尾汇总行下面, 按形态各补一行中性说明 (`跨设备目标 N 处默认跳过 (<该形态的解除路径>)`), 只有出现该形态时才输出;
- **不走 `--force`**: 这个旗标只放行「疑似安装树」这一类语义问题 (删了能不能重装恢复); 设备边界属于授权范围 (与安全闸的不变量同侧), 解除路径是改配置或卸载, 不是加旗标;
- **为什么逐条跳过, 而不是整批拒绝**: 安全闸的不变量一票否决整批, 因为那些事实 (根被替换 / 目标逃逸) 会让整批的可信度一起失效; 挂载点是**单个目标**的局部事实, 不会牵连同根下的其他目标, 所以只跳这一条, 其余照删。这一点和「语义闸」一样, 属于批次构造层的逐条判定, 不跟不变量同层;
- **核验不了就不判**: 设备号读不到时 (目标消失 / 权限不足 / 根不可解析), 不据此跳过; 没有检出就是没有证据, 归属、消失与复核等状态由安全闸的 `realpath` 和删除侧的逐级复核兜底;
- **误判登记 (保守的代价)**: 目标确实在另一个文件系统上、用户也确实想清理时, 要先显式声明该挂载点为根 (改一次配置), 或者先卸载; 反过来, 漏判的代价是删到授权路径之外的实际存储上、报告还写「成功」, 两个方向不对等, 所以取「先跳过、后声明」。

## 执行语义

- 删除动作只在 `--yes` 下发生 (默认只做预览, 见 [命令面与输出](../../../packages/sweep-node-modules-cli/docs/designs/cli-surface.md));
- **链头判定** (信任锚的防线, 第五道不变量在删除层的最小拦截): 每条删除前, 先看「配置拼写的根自身」是不是符号链接 (用 `lstat`, 不跟进), 是 → **整批中止**; `lstat` 核验不了时不因此拒绝 (权限噪声不升级为中止; 这种情形下 realpath 也解析不了, 目标会在更早的判定里被拒);
- **组件级安全复核** (TOCTOU 防线): 每条删除前, 从 roots 到 target 的父目录逐级 `lstat`, 任何一级组件是符号链接或不是目录 → **整批中止** (停止派发新条目, 已经在途的并发条目跑完; 没派发出去的条目一条都不删); roots 和 target 必须同源拼写 (调用方要先把 roots 做 realpath 化);
- **有界并发执行** (2026-09-29 性能审计裁定): 批次按「顺序派发、同时在途不超过 4 条」执行 (实测: 裸 `rm` 串行删 1200 条约 800ms, 4 路快 1.7 倍, 8 路因为 APFS 元数据锁竞争反而更慢)。三条安全属性不受并发影响: 每条内部「链头判定 → 逐级复核 → rm」的顺序原样保留 (收益来自并发, 不是砍掉复核: 实测复核只占 3% 的时间); 目标之间不嵌套 (扫描命中 node_modules 就剪枝), 任何一个目标的复核链都不可能落在别的目标的删除范围上; 中止 / 取消的定义是「停止派发 + 等在途条目跑完」(没派发的条目从不尝试; 取消时的 `partial` 收录所有已派发条目的结果; 多条并发同时检出中止时 (比如同一个根被替换), 报告的 `aborted` 取批次顺序里最靠前的触发条目, 和串行下的「第一个触发条目」一致, 不随调度方式变化)。分桶结果始终按输入顺序输出 (先收集后重排), 进度事件按完成顺序发出 (本来就不承诺事件顺序);
- **ENOENT 分阶段处理**: 复核阶段遇到组件 ENOENT → 归 `failed` (组件消失不等于目标消失, 目标可能只是被搬走、还在占盘, **不得报成功**; 文案里带「请复查目标是否仍存在; 未执行删除」); rm 阶段的 ENOENT **不能只看错误码下结论**: 两种运行时的语义有分歧 (实测见「残余风险」), Bun 会把「递归删除途中内部条目消失」冒泡成顶层 ENOENT, 而且错误对象和「顶层真的缺失」时逐个字段一模一样, 所以一律先复核目标本体 (`lstat`), 确认已经消失才归 `missing` (成功的一侧); 复核发现目标还在 (或复核不可达) → 归 `failed`, 文案「ENOENT: 删除中途失败 (复核确认目标仍存在 / 目标是否仍存在未能核验)」, 并附上内容残缺的复查提示;
- 逐条调用 `fs.rm(recursive)`, 单条 rm 失败不中断整批;
- 符号链接作为删除目标时: `fs.rm` 用的是 lstat 语义, 只删链接本身, 不跟随;
- 全部完成后打印结果汇总; 有失败或整批中止就返回退出码 1 (中止时另给「未执行删除 N 处」)。

## 残余风险 (安全复核的定量边界)

- **复核 lstat 与 rm 解析之间的窗口**: 实测 δ < 1.4µs, 攻击者最小的操作周期约 195µs (相差两个数量级); syscall 级振荡攻击下 322 次机会零越界: **现实中无法达到, 作为可接受项登记** (fd 级的 openat / O_NOFOLLOW 才是唯一彻底的解法, 但运行时没有暴露);
- **同形态真实目录的替换**: lstat 层识别不出来 (替换后对象仍在 root 内, 名字还是 node_modules); 它带来的假成功危害, 已由 ENOENT 的分阶段处理消除;
- **根锚点替换 (ANCHOR-REANCHOR, 本版已修)**: 上一版把「替换」一律登记在竞态窗口和同形态真实目录之下, **低估了其中一个方面**: 把根改名搬走、原地放一个符号链接指向别的目录树, 根本不需要竞态 (布置一次就持久生效, 离线也能做), 而且能把删除引到 root **之外**攻击者指定的目录树, 报告上还写「成功」, 归因指向的仍是配置里的原始拼写。本版在两处关掉了这个方面: 第五道不变量 (guard 层, 判整条锚点链) 和链头判定 (删除层, 判根自身); 判据看的就是拼写形态 (realpath 两边一起变, 看不出任何异常迹象)。这次的修法只覆盖「有链接插进来」这一种载体; 同形态真实目录的替换仍然识别不出来, 危害由 ENOENT 的分阶段处理兜住;
- **持续振荡能用很低的成本触发整批中止** (约 4% 的概率, 方向是 fail-safe): 没有数据损失, 登记为已知的 DoS 风险;
- **挂载点屏障只覆盖「目标本体就是挂载点」这一种形态, 而且两种运行时的行为不一致** (本机实测, 2026-09-27): 本节的设备边界闸只管「目标与根不同设备」; 目标**内部**还有子挂载点的形态不在判定范围内 (目标与根同设备, 挂载点在更深处)。这种形态的删除行为实测如下 (macOS HFS+ 映像, bun 1.4.2 / node v26.7.0): 目标本体就是挂载点时, 两种运行时都在 `rmdir` 处抛 `EBUSY`、**卷里的内容一点没动**; 目标内部有子挂载点时, **node 不会进入挂载点 (卷里的内容没动), bun 会进入、删掉卷里的内容, 但仍以 `EBUSY` 收尾**: 也就是说, 「挂载点是一道意外的屏障」这个说法只在 node 一侧成立, bun 一侧不成立 (差异的根源: node 的 rimraf 按错误码决定要不要进入挂载点, `EBUSY` 不属于让它进入的那类错误码; bun 的实现对目录先试着删、再进入)。所以对「目标内部有子挂载点」的目标, bun 一侧的删除会清空那个卷的内容, 而且属于**删掉的数据没法靠重装恢复**的一类。本轮不修的理由和候选修法见下一条; 现状里能接受的部分: 失败被如实上报 (`EBUSY` + 「内容可能已被部分或全部删除, 请复查」), 不是静默成功;
- **要检测目标内部的子挂载点, 得把整棵子树走一遍** (上一条里没有修的部分, 候选修法登记): 检出「目标内部有子挂载点」, 只能遍历目标子树、逐项比对 `st_dev` (又是一次和体积统计同量级的遍历), 或者自己实现一个带 one-file-system 语义的删除器 (替掉 `fs.rm`, 动到删除核心)。这两种做法都和本轮「最小改动」的权衡对不上; 而且 `du` 那边加 `-x` 只能把数字改对, 拦不住删除 (见 [扫描与体积](scan-and-size.md)「体积统计」)。所以本轮只把设备边界闸落在「目标与根」这一层, 这种形态登记为已知残留; 触发条件是用户把另一个卷挂进了某个 node_modules 内部 (比如容器里给 `node_modules/.cache` 挂卷), 属于部署时有意布置的, 不是攻击面;
- **判定与删除之间的窗口**: 跨设备判定在构造批次时做 (体积统计之后), 到 `rm` 之间如果有新挂载点出现 (自动挂载 / 手动挂载), 这个目标就会被跨设备删除; 窗口只在本次运行内存在几秒钟, 而且每次运行都会重新判定 (两次运行之间挂上去的挂载点, 下一次运行能发现)。不设删除层的复核, 这和已有的同类窗口是同一个取舍: 在窗口里挂上挂载点需要挂载权限, 而有挂载权限的人本来就不受这个工具约束, 登记为已知风险。
- **rm 阶段 ENOENT 的运行时语义分歧 (本版已加兜底复核, 本机实测 2026-09-27)**: 在「扇出很大的目录树 (240 个子目录) + 并发删除子项 (始终保留至少 2 个、绝不删根)」的竞态压测下, **node v26.7.0 把「递归删除途中内部条目消失」当成成功** (不冒泡, 40 轮没有一次报错; 和审计侧对该运行时内部实现的源码复核结论一致), **bun 1.4.2 会把它冒泡成顶层 ENOENT** (40 轮全部触发; 抛错后复核, 目标本体还在, 残留 169 到 236 个条目), 而且错误对象 (`code` / `syscall=lstat` / `path` / `message` 全都指向顶层目标) 和「顶层真的缺失」时逐个字段一模一样, 光看错误对象区分不出来。修复前, 这种情形会归进 `missing` (成功的一侧): 目标还占着盘, 报告里却是 ✓、退出码 0, 属于报告完整性的缺口, 不是数据损失。本版在 rm 阶段的 ENOENT 之后加了一次目标本体复核 (`lstat`): 确认已经消失才归 `missing`, 还在或复核不可达归 `failed`; 这次兜底不依赖运行时错误的形态 (Node 一侧走的是等价路径, 只是在该分支多一次 `lstat`)。这两种形态分别由 `delete.contract.test.ts` 的竞态压测 (bun 一侧, 10 轮实测全部落 `failed`; 旧实现下这个用例会 FAIL, 也是实测过的) 和 `delete.node-smoke.ts` 的 node 侧直跑 (实测不冒泡、没有伪成功) 钉住。触发条件是**并发的删除者** (另一个 sweep 实例 / 用户手工 rm / 包管理器清理), 不是远程攻击面, 而且出错方向偏保守 (报失败, 不是报假成功); Bun 内部为什么把子项的失败记成顶层 `lstat`, 没有查证源码, 登记为未核事实。

## 错误与边界

| 场景                          | 处置                                                                                                                                                                            |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 删除失败 (已尝试 rm)          | 逐条报错 + 「内容可能已被部分或全部删除, 请复查」, 末尾汇总, 退出码 1                                                                                                           |
| 安全闸拒绝 (包括根锚点这一类) | 逐条给出目标与理由 (根锚点这一类, 还要附上根和符号链接的定位以及怎么改写), 零删除, 退出码 1                                                                                     |
| 复核未完成 (组件已被替换)     | 整批中止, 未删除条目注明「未执行删除」, 退出码 1                                                                                                                                |
| 复核未完成 (根已被替换为链接) | 链头判定触发整批中止 (在删除层, 与安全闸构成纵深防御), 未删除条目注明「未执行删除」, 退出码 1                                                                                   |
| 复核未完成 (组件消失, ENOENT) | 该条记 `failed` + 「请复查目标是否仍存在; 未执行删除」(并附一句「若目标确已不存在, 可忽略此条」), 不牵连其余条目, 退出码 1                                                      |
| 目标已消失 (rm 阶段 ENOENT)   | 先复核目标本体, 确认已消失才归 `missing` (成功的一侧); 目标还在, 或复核不可达, 归 `failed`, 文案「ENOENT: 删除中途失败 (复核确认目标仍存在)」, 并附内容残缺的复查提示, 退出码 1 |
