## 校验不变量

任一删除目标必须同时满足, 否则整批拒绝 (保守优先):

1. 路径末段恰为 `node_modules` (对原始输入与 realpath 两者都判);
2. realpath 之后位于某个 `roots` 之下 (以 path.relative 语义判定, 禁字符串前缀比较; win32 按大小写不敏感);
3. 不是 `/` 本身, 也不是 home 本体;
4. realpath 去重后无重复目标;
5. **根锚点链**: 配置里的根 (原始拼写) 及其祖先链 (自根的一级子目录至根自身, 文件系统根本身不入链, 它不可能是符号链接), 逐级须为真目录 (lstat 判定, 不跟进末段); 任一级为符号链接 → 该根下的目标一律拒 (整批拒绝)。系统固有链接 (macOS 的 `/tmp`、`/var`) 同样命中, 改写为真实路径形态即放行; 根不可解析 (realpath 失败) 时该根无归属目标, 不牵连其余根。同一判定亦服务 `init` 的落盘目标 (写入侧的配置路径锚点检查, 读的是「链接会让写入改写其目标」), 见 [行为契约](../protocol/behavior-contract.md) BC-40。

**第 5 条的判据为何落在拼写而非 realpath 上**: `realpath(root)` 是同义反复 —— 无论配置里的名字被换成什么, 它只报告「此刻的解析结果」, 「名字 → 真实路径」这个映射被改动的事实无处可显; 而第 2 条与删除层复核链的比较两侧都取 realpath, 根被换位时一起漂移, 比较恒真。于是攻击者只需一次性 (无需竞态、持久生效、离线布置) 把根改名搬走、原地放符号链接指向他树, 此后每次 `--yes` 都会把删除导向那棵树, 且报告写「成功」。拼写形态是唯一能识破的证据。

**与 BC-11 的分工 (扫描跟进 ≠ 删除放行)**: [扫描算法](scan-and-size.md) 的「根自身为符号链接 → 照常扫描 (显式即授权)」管的是**扫描侧** (预览零副作用, 跟进链接无风险); 本节第 5 条管的是**删除侧信任锚**。同一场景下两者并存: 预览照常出清单, `--yes` 整批拒绝 —— 删掉的东西装不回来, 删除侧的门槛高于扫描侧, 两者不构成冲突。

## 语义闸: 疑似安装树缺省不进删除批

不变量判的是「路径形态与归属是否安全」, 不判「这个 node_modules 是不是用户的项目依赖」。向导默认根是家目录, 而家目录下的安装树 (包管理器的全局包树、版本管理器的 node 安装、编辑器扩展目录、系统 / 应用数据根) 同样满足这些不变量, 却不符合 ADR 0002 的删除合法性前提: 删后无法由项目级重装恢复 (本机实测 `~/.bun/install/global` 4.25 GB / 1627 包, 且本工具自身即装于其中; 版本管理器的 `lib/node_modules` 是用户全局包清单的唯一所在)。故在删除批构造处另加一道语义闸:

- **类别判定** (`classify.ts`, 纯函数, 只看路径形态, 三级逐条短路): ① `node_modules` 之上任一级目录名命中安装树容器名 (默认排除名单 ∪ `extensions` / `_npx`); ② `node_modules` 的父目录名为 `lib` (fnm / nvm / volta / asdf 的全局包一律落在 `<版本目录>/lib/node_modules`); ③ `node_modules` 位于家目录下的隐藏目录里 (应用私有根的惯例落点, 实测命中 `~/.oh-my-opencode` 237 MB、`~/.stepfun/releases/deps-6`、`~/.jcode/skills/archify` 等未收录进默认名单的应用根 —— 这批名字无法穷举, 故按形态兜)。命中任一条即判为**疑似安装树**, 其余判为项目依赖。大小写一律折叠比较 (多出来的误判落在安全侧), 判定不受用户配置影响 (用户删掉默认排除项, 这道闸仍在);
- **缺省行为**: 疑似安装树不进删除批, 并在执行报告按失败侧呈现 (行尾「已跳过 (加 --force 一并清理)」, 退出码 1 —— 与「未测到体积」同属「未处理目标」); 预览面据判定给出行尾标记并保留路径的 `node_modules` 后缀 (剥掉后缀会把安装树显示成项目);
- **放行通道**: `--force` 显式放行, 疑似安装树照常进入删除批; 它只影响批次构造, 不放宽安全闸的不变量, 也不改预览的零副作用语义;
- **误判面登记 (保守代价)**: monorepo 里名为 `lib` 的包 (`packages/lib/node_modules`)、名为 `extensions` 的容器、以及刻意藏在点目录里的项目 (`~/.my-project/node_modules`) 同样判为疑似 —— 判定只看路径而不看目录内容 (读内容会把判定与磁盘状态耦合: 竞态、权限噪声, 且越过纯函数边界), 家目录本体自身的 `node_modules` 不受影响 (它仍按项目判, 家目录本身即可是一个工作区)。误判的代价是加一次 `--force`, 方向落在安全侧; 反向 (把真安装树判成项目) 才是不可逆的损失。

## 设备边界: 跨设备目标缺省不进删除批

不变量判的是「路径形态与归属是否安全」, 语义闸判的是「删后能否由项目级重装恢复」, 两者都不看目标落在**哪个文件系统**上。根只是路径上的授权面: 根之下的挂载点 (云盘 / 网络挂载 / 容器卷) 会把另一文件系统的内容带进这条路径, 于是「根之下的 node_modules」可能在另一块盘、另一台机器上。跨设备删除删的是授权路径之外的实际存储 (远端文件系统的删除往往没有回收站可退, 还可能被同步到别处), 且删除量与根所在卷的释放量不再是同一口径, 故在删除批构造处另加一道设备边界闸:

- **判定** (`guard.ts` 的 `findCrossDeviceTargets`): 逐条比对目标与其所属根的 `st_dev`; 目标取 `lstat` 语义 (与 `fs.rm` 的末段语义对齐 —— 目标是符号链接时只删链接, 不跨设备), 根取 `stat` 语义 (根解析到的实际目录才是参照面)。归属取**最具体的根** (包含该目标且路径最长的那个): 设备比对需要唯一参照面, 而把挂载点声明为独立根就是「这个卷归我处置」的显式表达;
- **两形态分列** (解除路径不同, 故不混作一句): `on-path` = 挂载点在根与目标之间 (目标与父目录同设备), 解除路径是**把该挂载点声明为独立根** (写进配置 `roots` 或加 `--config`), 声明后该目标归属它、设备比对通过、照常删除; `target-itself` = 目标本体即挂载点 (目标与其父目录不同设备, 卷内的数据不在本目标的删除面内), 声明根无济于事, 只能先卸载该卷 —— 而且即便放行, 挂载点的 `rmdir` 也必然 `EBUSY` (卷不能靠删目录卸掉);
- **缺省行为**: 跨设备目标不进删除批, 预览面行尾按形态标注 (`跨设备: 根与目标之间有挂载点` / `跨设备: 目标本体即挂载点`), 执行报告按失败侧呈现 (行尾「已跳过 (把该挂载点声明为独立根即可清理)」/「已跳过 (挂载点无法删除, 需先卸载该卷)」), 退出码 1 (与疑似安装树同属「未处理目标」); 末行之下按形态各补中性说明行 (`跨设备目标 N 处默认跳过 (<该形态的解除路径>)`), 只在出现该形态时出;
- **不走 `--force`**: 该旗标只放行「疑似安装树」这一语义面 (删后能否重装恢复), 设备边界属授权面 (与安全闸的不变量同侧), 解除路径是改配置或卸载, 不是旗标;
- **为何逐条跳过而非整批拒绝**: 安全闸的不变量一票否决整批, 因为那些事实 (根被换位 / 目标逃逸) 会让整批的可信度一起失效; 挂载点是**单个目标**的局部事实 —— 它不牵连同根下的其余目标, 故只跳该条, 其余照删。这一点与「语义闸」同为批次构造层的逐条判定, 不与不变量同层;
- **不核验即不判**: 设备号读不到 (目标消失 / 权限不足 / 根不可解析) 时不据此跳过 —— 未检出即无证据, 归属、消失与复核等态由安全闸的 `realpath` 与删除侧的逐级复核兜底;
- **误判面登记 (保守代价)**: 目标确实位于另一文件系统且用户确实想清理时, 需先显式声明该挂载点为根 (一次配置改动) 或卸载; 相对地, 漏判的代价是删到授权路径之外的实际存储上、且报告写「成功」, 两者方向不对等, 故取「先跳过、后声明」。

## 执行语义

- 删除动作只在 `--yes` 下发生 (预览默认, 见 [命令面与输出](../../../packages/sweep-node-modules-cli/docs/designs/cli-surface.md));
- **链头判定** (信任锚防线, 第五道不变量的删除层最小拦截): 每条删除前先判「配置拼写的根自身」是否为符号链接 (`lstat` 不跟进), 是 → **整批中止**; `lstat` 不可核验时不据此拒绝 (权限噪声不升级为中止, 该情形下 realpath 亦不可解析, 目标会在更早的判定里被拒);
- **组件级安全复核** (TOCTOU 防线): 每条删除前, 自 roots 至 target 父目录逐级 `lstat`, 任一组件为符号链接或非目录 → **整批中止** (停止派发新条目, 并发在飞条目跑完; 未派发条目一条不删); roots 与 target 须同源拼写 (调用方须先 realpath 化 roots);
- **有界并发执行** (2026-09-29 性能审计裁定): 批次按「顺序派发、在飞 ≤ 4」执行 (实测: 裸 `rm` 串行约 800ms/1200 条, 4 路 1.7×, 8 路因 APFS 元数据锁竞争回退)。三条安全属性不受并发影响: 条内「链头判定 → 逐级复核 → rm」的时序逐字保留 (收益来自并发而非砍复核——复核实测仅占 3%); 目标间不嵌套 (扫描对 node_modules 命中即剪枝), 任一目标的复核链不可能落在别条目标的删除面上; 中止 / 取消定义为「停止派发 + 等在飞排空」(未派发条目从不尝试; 取消的 `partial` 收录全部已派发条目的结果; 多条并发检出中止时 (如同一个根被换位), 报告的 `aborted` 取批次序最前的触发条——与串行「首个触发条」一致, 不随调度漂动)。分桶恒按输入顺序输出 (收集后重排), 进度事件为完成序 (事件序本不承诺);
- **ENOENT 阶段两分**: 复核阶段组件 ENOENT → `failed` (组件消失 ≠ 目标消失, 可能被搬走仍在占盘, **不得报成功**; 文案含「请复查目标是否仍存在; 未执行删除」); rm 阶段 ENOENT **不以错误码本身定论**: 双运行时语义分叉下 (实测见「残余风险」), Bun 会把「递归途中内部条目消失」冒泡为顶层 ENOENT 且错误形态与顶层缺失逐字段同形, 故一律先复核目标本体 (`lstat`), 确认已消失才归 `missing` (成功侧); 复核发现目标仍在 (或复核不可达) → 归 `failed`, 文案「ENOENT: 删除中途失败 (复核确认目标仍存在 / 目标是否仍存在未能核验)」并附内容残缺复查提示;
- 逐条 `fs.rm(recursive)`, 单条 rm 失败不中断整批;
- 符号链接作删除目标: `fs.rm` 取 lstat 语义, 只删链接本身, 不跟随;
- 全部完成后打印结果汇总; 存在失败或整批中止即退出码 1 (中止另给「未执行删除 N 处」)。

## 残余风险 (安全复核的定量边界)

- **复核 lstat 与 rm 解析之间的窗口**: 实测 δ < 1.4µs, 攻击者最小操作周期约 195µs (相差两个数量级); syscall 级振荡攻击 322 次机会零越界 — **现实不可达, 可接受登记** (fd 级 openat / O_NOFOLLOW 是唯一终解, 运行时未暴露);
- **同型真实目录换位**: lstat 层不可识别 (换位后对象仍在 root 内且名为 node_modules); 其「假成功」危害面已由 ENOENT 阶段两分消除;
- **根锚点换位 (ANCHOR-REANCHOR, 本版已修)**: 上一版把「换位」一律登记在竞态窗口与同型真目录之下, **低估了其中一维**: 把根改名搬走、原地放符号链接指向他树不需要任何竞态 (一次布置、持久生效、离线可做), 且可把删除导向 root **外**的攻击者选定树, 而报告写「成功」、归因指向配置里的原始拼写。本版以第五道不变量 (guard 层, 判整条锚点链) 与链头判定 (删除层, 判根自身) 双处关闭该维, 判据落在拼写形态上 (realpath 两侧一起漂移, 无症可显); 修法只覆盖「链接介入」这一载体 —— 同型真实目录的换位仍在不可识别之列, 其危害面由 ENOENT 阶段两分兜住;
- **持续振荡可低成本触发整批中止** (约 4% 概率, fail-safe 方向): 无数据损失, 登记为已知 DoS 面;
- **挂载点屏障只覆盖「目标本体即挂载点」一形, 且两种运行时行为分叉** (本机实测, 2026-09-27): 本节的设备边界闸管的是「目标与根不同设备」, 目标**内部**含有子挂载点的形态不在判定面内 (目标与根同设备, 挂载点在更深处)。该形态的删除行为实测如下 (macOS HFS+ 映像, bun 1.4.2 / node v26.7.0): 目标本体即挂载点时, 两种运行时都在 `rmdir` 处 `EBUSY` 上抛、**卷内内容逐字未动**; 目标内部含子挂载点时 **node 不下探 (卷内内容未动), bun 下探并删除卷内内容后仍以 `EBUSY` 收尾** —— 即「挂载点是意外屏障」这一说法只在 node 侧成立, 在 bun 侧不成立 (差异根源: node 的 rimraf 按错误码决定是否下探, `EBUSY` 不在其下探集合内; bun 的实现对目录先试删再下探)。故对「目标内部有子挂载点」的目标, bun 侧的删除会清空该卷内容, 且属**已删除数据不可由重装恢复**的一类。本轮不修的理由与候选修法见下条; 现状的可接受面: 失败被如实上报 (`EBUSY` + 「内容可能已被部分或全部删除, 请复查」), 不是静默成功;
- **目标内部子挂载点的检测需要一次整棵子树走查** (上条的未修面, 候选修法登记): 检出「目标内部有子挂载点」只能靠遍历目标子树比对 `st_dev` (另一次与体积统计同量级的遍历), 或改由自实现的删除器实现 one-file-system 语义 (替换 `fs.rm`, 触碰删除核心)。两者都与本轮「最小改动」权衡不匹配, 且 `du` 侧加 `-x` 只能改数字、不能拦删除 (见 [扫描与体积](scan-and-size.md)「体积统计」), 故本轮只把设备边界闸落在「目标与根」这一层, 该形态登记为已知残留; 触发条件是用户把另一个卷挂进了某个 node_modules 内部 (如容器里给 `node_modules/.cache` 挂卷), 属部署期显式布置而非攻击面;
- **判定与删除之间的窗口**: 跨设备判定在批次构造时做 (体积统计之后), 到 `rm` 之间若新挂载点出现 (自动挂载 / 人工挂载), 该目标会跨设备删除; 窗口是本次运行内的秒级段, 且每次运行都重判 (人工复核两次运行之间的挂载布置因此能被抓到)。不设删除层复核与既有同类窗口同一取舍: 窗口内布置挂载需挂载权限, 且有权限者不受本工具约束, 登记为已知面。
- **rm 阶段 ENOENT 的运行时语义分叉 (本版已加兜底复核, 本机实测 2026-09-27)**: 大扇出树 (240 子目录) + 并发删子项 (恒保留 ≥ 2 个、绝不删根) 的竞态压测下, **node v26.7.0 把「递归途中内部条目消失」归一为成功** (不冒泡, 40 轮零拒绝; 与审计侧对该运行时内部实现的源码复核结论一致), **bun 1.4.2 会把它冒泡为顶层 ENOENT** (40 轮全中, 抛错后复核目标本体仍在、残留 169 至 236 个条目), 且错误形态 (`code` / `syscall=lstat` / `path` / `message` 全指向顶层目标) 与「顶层真缺失」逐字段同形, 单看错误对象无法区分。修复前该形态落 `missing` (成功侧): 目标仍占盘而报告 ✓、退出码 0, 属报告完整性缺口而非数据损失。本版在 rm 阶段 ENOENT 后加一次目标本体复核 (`lstat`): 确认已消失才归 `missing`, 仍在或复核不可达归 `failed`; 兜底不依赖运行时错误形态 (Node 侧为等价路径, 只在该分支多一次 `lstat`)。两形态由 `delete.contract.test.ts` 的竞态压测 (bun 侧, 10 轮实测全落 `failed`; 旧实现下该用例 FAIL 已实测) 与 `delete.node-smoke.ts` 的 node 侧直跑 (实测不冒泡、无伪成功) 钉住。触发条件是**并发删除者** (另一个 sweep 实例 / 用户手工 rm / 包管理器清理), 非远程攻击面, 且失误方向落在保守侧 (报失败而非伪成功); Bun 内部为何把子项级失败记成顶层 `lstat` 未查证源码, 登记为未核事实。

## 错误与边界

| 场景                         | 处置                                                                                                                                                            |
| ---------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 删除失败 (rm 已尝试)         | 逐条报错 + 「内容可能已被部分或全部删除, 请复查」, 末尾汇总, 退出码 1                                                                                           |
| 安全闸拒绝 (含根锚点)        | 逐条给出目标与理由 (根锚点类附根与符号链接的定位及改写指引), 零删除, 退出码 1                                                                                   |
| 复核未完成 (组件被替换)      | 整批中止, 未删除条目注明「未执行删除」, 退出码 1                                                                                                                |
| 复核未完成 (根被替换为链接)  | 链头判定整批中止 (删除层, 与安全闸互为纵深), 未删除条目注明「未执行删除」, 退出码 1                                                                             |
| 复核未完成 (组件消失 ENOENT) | 该条 `failed` + 「请复查目标是否仍存在; 未执行删除」(并附「若目标确已不存在, 可忽略此条」), 不牵连其余条目, 退出码 1                                            |
| 目标已消失 (rm 阶段 ENOENT)  | 复核目标本体确认已消失才归 `missing` (成功侧); 目标仍在或复核不可达归 `failed`, 文案「ENOENT: 删除中途失败 (复核确认目标仍存在)」并附内容残缺复查提示, 退出码 1 |
