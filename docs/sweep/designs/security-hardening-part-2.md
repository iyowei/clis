`sweep-node-modules` 干的事很朴素: 在工作区里找散落的 `node_modules`, 量出体积, 删掉。它立过一套相当克制的纪律: 预览默认、`--yes` 才动手, 动手前每个目标还要过一组不变量与两道批次闸。[前篇](install-tree-hardening.md) 记过其中两处大修: 删掉的东西要能回来 (默认排除名单与语义闸), 要删的地方还得是原来那个 (根锚点链)。

第 1 批修完之后, 审计没有停。第二批 (第 3~11 条) 把目光从删除动作本身移开, 去看它周围的每一环: 它说出口的话、写下的字、发布时的身份、跑起来时伸手取用的东西, 以及删除面自己剩下的角落。这一批还多了一层特别之处: 审计报告里的条目本身, 也要反过来逐条接受证据的检验。九条里, 一条的结论经实测只成立一半, 一条的前提被三重证据证伪, 一条被整体否决。

> 第 1 批管的是删除动作的两半; 第 2 批管的是这个动作之外、与之相连的每一环。审计报告在这里不是判词, 是待核验的假设清单; 修复面按核验结果来画。

## 它说的话, 也是输出面

工具早就有一套「净化」: 清单里的显示名若含控制字符, 先剥净再展示, 行尾标注「名字已净化显示」。理由直接: 磁盘上的目录名是外部数据, 谁都能让一个名字里夹带控制字节。

但净化只做在清单上。诊断面 (stderr 上的告警与错误) 此前是裸的, 而它装着的恰恰是最脏的数据: 磁盘路径、`du` 的报错原文、名单里写的名字、命令行参数原文。这些数据里的控制字节不会经过任何净化: 换行能把一条告警劈成两行, 后半截看上去像是工具自己吐出的另一条可信输出; ANSI 逃逸序列会被终端执行, 也会被 CI 日志原样收下, 日后回放时再执行一遍。

更要紧的是位置: `--yes` 流程下 stdout 的清单是空的, 诊断面是删除前唯一可见的信息。最脏的数据、最要紧的位置、唯一没设防的面, 三样凑在了一起。

修法是把净化集中到一个统一出口: 从此清单显示名、stderr 的告警与错误、`config` 报告里的路径、向导的路径回显行、`--help` 的默认配置位置行, 全部经过同一份实现, 各面不得另写一份。剥离集覆盖 C0 (含 ESC)、DEL、C1、bidi 控制、零宽、BOM 等各类字符, 剩余空白 (含换行) 折成单空格; 净化发生在工具自己的着色之前, 所以非 TTY 输出里必不含 ESC。语义一句话: 复述外部数据的地方, 就是输出面; 输出面不按位置划分, 按数据来源划分。

集中净化时, 又连带抓出一处漏网: 帮助页的「默认配置位置」行。它是最不像输出面的输出面: 帮助文本看上去和外部数据无关; 但那一行里嵌着平台的默认路径, 路径来自环境。这里现在也要过同一份净化。

一处刻意留下的例外要交代: 向导的落盘回显块不净化。它回显的是本轮用户自己的答案, 承诺的是与落盘文件逐字一致、可供对照复制; 净化会破坏这个承诺。界线登记在案 (该块对 JSON 转义覆盖不到的字符类以原样保留, 属已知缺口, 接受)。

## 同一个锚点, 换到写入侧

前篇讲过一个会被掉包的根: 门卫逐单核对, 但没有一步核对过柜子本身还是不是原来那个。修法是第五道不变量加上链头判定, 判据落在路径的拼写上。

第二批审计问了一个自然的问题: 这套锚点只护着删除吗? 写入这个动作, 该问的其实是同一件事: 落点, 还是不是看上去的那个?

`init` 向导的落盘环节对此给出了否定的答案。配置路径 (或其祖先链) 上有符号链接时, 写入会跟随链接; 被完整改写的是链接指向的文件, 而回执报的还是用户当初写下的那串路径。放在共享目录或别人的仓库里, 链接可能是别人预先布置好的: 确认框写着「覆盖 config.json」, 被覆盖的却是链接那一头任意一个可写文件。事前看不出, 事后也看不出, 回执从头到尾只把用户写下的路径复述一遍。

修法与删除侧同源: 同一套判定、同一份实现 (`guard.ts` 的锚点检查), 对链的判定不因末端是文件还是目录而不同。检查时机在确认写入之后、任何写动作 (含建目标目录) 之前: 逐级 `lstat`, 任一级是符号链接 (悬空链接同样命中) 即拒, 一个字节不落, 给出链接的位置与配置路径, 重新问一遍「确认写入?」。系统自带的链接 (macOS 的 `/tmp`、`/var`) 同样命中, 改写成真实路径形态即可放行。

顺手记一处两次询问的先后: 配置路径是悬空链接时, 是否覆盖的判定按 `lstat` 语义也会把它算作「已存在」, 于是这类路径会先被问一遍是否覆盖, 随后才在写入侧被拒。顺序已登记, 不是漏洞。

至此, 同一个锚点判定在两个地方各站一班岗: 删除侧判信任根 (根被换位), 写入侧判落盘目标 (写入会跟随链接, 改写它指向的目标)。两边看的是同一个坐标: 拼写, 与它此刻指向哪里。条款编号 BC-40 记的就是后一班岗。

## 被评审的源码, 与被执行的字节

发行链上有三段各自有道理的设计: 本地入口「有构建产物就优先跑产物」; 发布从当前工作树现场构建; 产物不入库 (随发布生成, `.gitignore` 忽略)。

三段合起来, 就是一件没人明说的事: 被评审的源码和被执行的字节之间, 没有任何能被核对的对应关系。维护者读的、测的、评审的是 `src/`; 安装者跑的, 是某次构建从某棵工作树上现场做出来的 `dist/cli.js`。工作树脏不脏, 构建不看; 产物对应哪个提交, 产物不写; 二者对不上, 也没人核。像一份图纸与一栋楼: 图纸摆在评审桌上, 楼在别处施工, 两者之间没有任何一步核对, 也没有任何凭证能看出楼是按哪一版图纸建的。

漂移也不是假设: 本工作树的产物落后源码两次提交。维护者与安装者都在跑一个没人核对过出身的东西。

修法三层, 各堵一段:

**发布前置闸门** (`bun run verify:release`) 挂在 `prepublishOnly`, 四项按序短路, 任一不满足即退 1 拒发: 工作树干净 (`git status --porcelain` 为空, 含未跟踪文件); 产物就位 (`dist/cli.js` 存在且非空); 清单自洽 (清单记录的提交等于 HEAD、构建时工作树干净、摘要等于产物实测值); 发行包内的文件与白名单相符 (以只读方式跑一次 `npm pack --dry-run --json --ignore-scripts` 收清单, 与白名单常量 (`PACK_FILES_EXPECTED`) 逐项对账, 多出或缺少的分别列出)。

**产物自证清单**: 构建同时产出 `dist/manifest.json`, 记下源提交、构建时工作树的脏净状态、产物摘要、构建时间与形状版本。启动器在启用产物之前, 先与清单对账: 缺失、损坏、版本不支持、摘要不符, 一律拒收该产物并给出指引 (仓库检出态给源码入口与重新构建, 包态给重装本包), 不静默回退源码。产物从今天起随身带一张身份证, 上面写着自己的出身; 对不上就不出场。

**白名单常量**: 把「发行包里应该有哪些文件」写成断言, 防复发。它具体防着一件事, 值得单独讲。

> npm 会把仓库根的 `README*` / `LICENSE*` 无条件收进发行包, 且没有任何配置可以排除。

这不是经验之谈: npm 官方 `files` 节原文写着 "Certain files are always included, regardless of settings", 实现侧也印证了这一点 (npm-packlist 里对包根 README / LICENSE 的硬编码规则, 独立于 `files` 与 `.npmignore`)。于是落在仓库根的一份 README 备份, 会被静默发出去。治前实测: 包清单 8 项, 含两份 README 备份; 治后 6 项 (当轮快照; 后在白名单增补 `README.zh-CN.md` 一项, 现为 7 项, 以 `release-artifact.ts` 的 `PACK_FILES_EXPECTED` 实时内容为准)。打包规则里写着「这几样永远随车」, 不设例外通道; 对策只能是: 把不该上车的移出仓库 (备份落 `~/tmp`), 再让白名单断言常驻, 防止复发。

闸门的触发面查过了, 边界如实交代: `npm publish` 与 `bun publish` 都在闸门内 (`bun publish` 的结论来自官方测试与源码核证, 不是凭印象); 已知的漏口是 `npm pack` 与 `npm publish <tarball>`: 打好的包再发布, 不经这道闸。不补 `prepack` 兜底的理由: `npm pack --dry-run` 是常用的只读查看动作, 挂上闸门会让它在脏树 / 未构建时硬失败, 代价大于收益; 这个漏口的补救, 是白名单断言已在闸门内覆盖同一类风险。本节的闸门与自证设计, 完整规格见 [ADR 0009](../../adrs/0009-npm-distribution-form.md) 补记。

## 根之下的另一块盘

不变量判「路径形态与归属是否安全」, 语义闸判「删后能否由重装恢复」; 两道闸问的都是路径。而根只是路径上的授权面, 根之下可以挂载另一块盘 (云盘 / 网络挂载 / 容器卷)。「根之下的 `node_modules`」完全可能在另一块盘、另一台机器上。跨设备删除, 删的是授权路径之外的实际存储; 远端文件系统的删除往往没有回收站可退, 还可能被同步到别处; 删除量与根所在卷的释放量, 也不再是同一个口径。授权写在地址上, 而地址经过的那道门, 背后可以是别人家的仓库。

审计的第一版结论给过一颗定心丸: 挂载点会甩出 `EBUSY`, 是「意外屏障」。hdiutil 真机实测 (HFS+ 映像) 把这颗定心丸劈成了两半:

- 目标本体即挂载点: bun 与 node 都在 `rmdir` 时抛出 `EBUSY`, 卷内内容逐字未动。屏障成立;
- 目标内部含子挂载点: node 不下探, 卷内内容未动; bun 会下探, 删除卷内内容后仍以 `EBUSY` 收尾。屏障不成立。

而本工具的主载体恰好是 bun (业务逻辑 Bun 优先)。差异的根源在实现: node 侧的 rimraf 按错误码决定是否下探, `EBUSY` 不在它的下探集合里; bun 对目录先试删再下探。同一句话, 换个运行时就成了反的。

修法是设备边界闸: 逐条比对目标与其所属根的 `st_dev` (设备号), 不同设备即跳过。参照面取最具体的根: 把挂载点声明为独立根, 就是「这个卷归我处置」的显式表达; 目标取 `lstat` 语义 (目标是符号链接时只删链接, 不跨设备), 根取 `stat` 语义 (根解析到的实际目录才是参照)。

为什么逐条跳过, 而不是像不变量那样整批拒绝? 因为事实的范围不同: 根被换位、目标逃逸会让整批的可信度一起失效; 挂载点是单个目标的局部事实, 不牵连同根下的其余目标。同一层级的判定, 失效波及面不同。

两种形态的解除路径各按事实: 挂载点在根与目标之间 (on-path), 把该挂载点声明为独立根即可照常清理; 目标本体即挂载点 (target-itself), 声明根无济于事, 只能先卸载该卷, 而且即便放行, 挂载点的 `rmdir` 也必然 `EBUSY`, 卷不能靠删目录卸掉。两支都不走 `--force`: 那个旗标是「疑似安装树」的钥匙, 不是关掉安全闸的开关。

残余风险也如实记在案: 「目标内部含子挂载点」这一形态, 本轮不修。检出它需要一次整棵子树的走查 (与体积统计同量级的遍历), 或自实现删除器 (触碰删除核心); 触发条件是用户把另一个卷挂进某个 `node_modules` 内部 (部署期显式布置, 不是攻击面)。现状还能接受的理由是: 失败会被如实上报 (`EBUSY` 加「内容可能已被部分或全部删除, 请复查」), 不是静默成功。要强调的是 bun 侧下探的后果: 卷内内容被清空, 且属于「删了回不来」的那一类。

另有一个秒级窗口登记在案: 设备判定在批次构造时做, 到 `rm` 之间若新挂载点出现 (自动挂载 / 人工挂载), 该目标会跨设备删除; 不设删除层复核, 与既有同类窗口同一取舍; 布置挂载需要挂载权限, 而有挂载权限的主体不受本工具约束。

## 退出码 0, 磁盘还占着

有一个竞态场景: 工具在删一棵大树的途中, 另一只手也在删同一棵树 (另一个实例、用户手工 `rm`、包管理器的清理)。子项被抢先删掉, `fs.rm` 会撞上 ENOENT。审计留下的一个假设是: Bun 的 `fs.rm` 对这种情况还没核过 (Node 侧已证明不会冒泡)。

实机实测把一个运行时差异挖了出来:

- node: 「递归途中内部条目消失」按成功处理, 不冒泡;
- bun: 把它冒泡为顶层 ENOENT, 而错误对象的每个字段 (`code` / `syscall` / `path` / `message`) 都指向顶层目标, 与「顶层真缺失」逐字段同形, 单看错误对象分不出是哪一种。而此时目标树还在。

修复前, 这个形态落进 `missing` (成功侧): 报告 ✓、退出码 0、磁盘还占着。竞态压测下 20/20 伪成功。这不造成数据损失 (东西还在), 但它直接违背工具的失败响亮原则; 报成功而没成功, 是报告完整性缺口。

修法有一个转向: 不靠错误对象判定, 同形的东西没法分; 改为事后复核目标本体 (`lstat`, 三种结局): 确实没了, 才归「缺失」; 还在, 或核不到, 一律归「失败」。兜底不依赖运行时错误形态 (Node 侧是等价路径, 只在该分支多一次 `lstat`)。错误对象像一张状态单, 而这张单子会被填成同一个样子; 修复是不再看单子, 亲自去门口看一眼。

压测把两侧都覆盖了: bun 侧竞态压测实测全落「失败」; node 侧直跑实测不冒泡、无伪成功; 旧实现下该用例 FAIL 有实测记录。

两个未尽的注脚, 一并如实交代: 复核不可达时归「失败」, 方向落在保守侧, 宁可误报失败让人去复查, 也不误报成功; Bun 内部为何把子项级失败记成顶层错误形态, 未查证源码, 登记为未核实事实。

## 它走进别人家的时候

本工具会被作为依赖装进别人的仓库 (vendor 目录、本地路径、git 依赖都是形态之一)。审计在这条路上抓到两条链, 通向同一个结果: 把本包装进任何一个使用方仓库, 使用方仓库里就会多出它的 git 钩子。

第一条链: `prepare` 脚本直接调 `lefthook install`, 装到哪, 就认哪儿的 git 仓库。作为依赖装进别人仓库时, 钩子被写进**使用方**的 `.git/hooks`; vendor / 本地路径形态实测坐实。

第二条链: 只要 lefthook 留在 `devDependencies`, 使用方安装本包时会被连带装上它; 而它自带 `postinstall`, 且被包管理器的默认信任名单放行 (bun 的内置名单含它), 于是它的 `postinstall` 也会去写使用方钩子。两条链互为备份, 堵住一条, 还有另一条。

修法对应两刀, 加两个保险 (设计依据见 [ADR 0005](../../adrs/0005-engineering-gates-and-hooks.md) 决策第 1 条):

- `prepare` 换成守卫脚本 (`scripts/install-git-hooks.mjs`): 只在本包自身的 git 仓库根 (cwd 所在 git 根即包根) 执行装钩子; 被作为依赖安装时整支跳过, 不写使用方仓库; CI 下短路; 装钩子失败也不阻断依赖安装。
- lefthook 移出依赖: 不再往依赖树里预装; 要用时改为「PATH 上的全局安装优先, 没有就用 `bunx` 取 pin 版」。
- 钩子执行链两个官方配置键: 命令兜底 (`bunx lefthook@<pin>`) 让无全局 lefthook 的机器照常跑; `assert_lefthook_installed: true` 让它找不到时响亮失败。

第二个保险是复核时补的, 值得单独讲, 因为它修的是另一种病: 静默失效。官方生成的钩子模板, 探测 lefthook 的顺序全链不含 `bunx`; 而 `assert_lefthook_installed` 默认关闭时, 全链找不到 lefthook 只 echo 一行提示然后按 0 退出。翻译过来是: 钩子装上了, 执行时门禁悄悄失效。这正是「装 ≠ 可执行」的验收教训: 只验「装没装上」, 会漏掉执行链空转; 必须验「无全局 lefthook 的机器上, 门禁也能真正立起来」。两个键都配上之后: 净化 PATH 的实测里, 钩子经 `bunx` 兜底照跑; 确实全链不可用时退非零, 不再静默放行。

修复面经临时消费者仓库三形态实测 (npm + vendor、bun + 本地绝对路径、npm + git 依赖): 修复后三形态的使用方 hooks 均保持基线干净, 而本包仓库检出态的装钩子功能不变。开发者体验零倒退: 不再往依赖树里预装 (零预装), 任何机器都能按需取到 (全局安装或 `bunx` 兜底); 两者都不可用时, 依赖安装照常完成, 只少一副钩子, 有一行提示, 可按需补装。

## 它从哪个目录里捡起运行时

本工具有一个别人没有的处境: 它恰好在**被扫目录里**执行。它跑起来的地方, 就是它要扫的地方, 而那些目录里住着别人的项目。

Windows 上的裸名执行, 把处境变成了入口: `CreateProcessW` 的搜索序把当前目录排在 PATH 之前 (微软官方文档: 搜索序第 2 位即 the current directory for the parent process); Node 走的 libuv 同样先试 cwd 再扫 PATH, 且只试 `.com` / `.exe` 两个扩展名 (微软官方文档与 libuv 源码双证)。于是: 在被扫目录里放一个 `bun.exe` (或 `bun.com`), 启动器喊「bun」时, 先应声的就是它。像喊一个名字, 先应声的是房间里站着的人, 而不是通讯录上的那位; 而被扫的目录, 恰恰是一间外人能进出的房间。

修法是三个入口的运行时解析统一排除当前目录 (依据见 [ADR 0007](../../../packages/sweep-node-modules/docs/adrs/0007-platform-portability.md) 决策第 4 条补记): npm 入口 (`.mjs`) 在 win32 下先按 PATH 解析绝对路径再执行 (空条目与相对条目跳过, 两者在 Windows 上都表示当前目录); cmd 入口改用 `for` 的 PATH 展开修饰符, 只搜 PATH; sh 入口的 `command -v` 与 `exec` 本就只按 PATH。

同一次审计还带出一处同型修复: 体积统计的 `du` 探针是 POSIX 绝对路径 (`/usr/bin/du`), 在 win32 上会被解析成「当前盘根」下的 `usr\bin\du`, 该盘上若存在同名外来程序, 被调起的就是它。守卫加在探针上: win32 一律返回「无 `du`」, 走纯实现基线, 与「du 快路径仅 unix」的既有口径对齐。

边界也画清楚了, 如实登记: 三入口的候选名搜索粒度在 win32 上并不一致 (cmd 是扩展名优先, libuv 与 npm 入口是目录优先), 仅当多个 PATH 目录分别存在不同扩展名的二进制时才可能选中不同目标; 另有两条同型现象经核实不在本仓防御面内, 各自登记 (npm 生成的 cmd-shim 以裸名调起本包入口, 属包管理器产物面; 守卫脚本自身的 win32 裸名调用, 属开发工具链面)。而 win32 解析防御的实跑, 归入「真机未验」的缺口, 如实挂着。

## 被证伪的前提, 与被否决的条目

九条审计条目里, 有一条的前提在核实中倒下了。

审计的推理链是: GNU `du` 在非终端下会转义路径, 输出无法与输入一一对应, 触发既有的整批降级, 清理于是静默 no-op。逐条核实的结果, 第一环就站不住: GNU coreutils 手册写的是相反的适用条件 ("When standard output is a terminal, file names are quoted using the shell-escape style"), coreutils 源码里的引用逻辑由 `isatty` 控制 (9.12 之前的版本根本没有引用逻辑), 实测 (GNU du 9.12 与 BSD du) 也印证了这一点; 而且这条快路径用管道捕获 stdout, 永远不是终端。该形态不可达。

链条的其余部分是真的: 整批降级机制确实存在 (输出与输入集合不符即整体降级, 防止把错误输出按行采信); 它仍可能被别的形态触发 (行结构被注入破坏, 或那个前提真有一天被推翻)。所以修法不为不可达形态写代码, 只补可诊断性: 整批降级时随附一条按形态归类的告警, 让「什么都没删」可以被归因, 不静默。顺手的收尾: 修正仓库里两处与事实相反的注释。

另一条被整体否决: 「删除面无上界, 且 `--yes` 不展示 roots」。复核认为不成立: `roots` 的三个来源 (旗标、环境变量、平台默认配置) 都是属主自己的通道, 能往这些通道里注入的人, 本来就有同等权限, 是自己给自己挖坑, 不构成跨边界。处置: 这条披露缺口转为「产品改进项」, 不在安全面上修。

两条合看, 恰是这一批最该被记住的方法论: 审计条目和代码一样, 要过核实这一关。证伪一条, 省下的不是一行代码, 而是「为一个不存在的敌人修一堵墙」的全部成本; 否决一条, 免的是「为一个不跨界的担心加一套机制」的未来负担。

## 九轮扫描: 修复的另一半是更新

一个安全发现的修复, 动作其实有两半: 一半是改代码 (修复的正确性); 另一半是把每一处登记面都更新 (设计文档、行为契约、帮助文案、README、注释)。后一半失败的方式很安静: 代码对了, 而某份文档还在教旧行为; 断言对了, 而某处注释还在写反的语义。

这一批的做法是: 修完之后, 以「连续 3 轮独立影响面扫描、每轮对全部修复逐条零遗漏」为收敛判据; 实际跑到第 9 轮才满足, 前六轮每轮都扫出登记面遗漏并逐一处置, 后三轮干净达成。前六轮每轮都有发现, 说明单轮扫描的覆盖不成立; 后三轮的干净, 才是收敛信号。

这与修复正确性的验收是同一种纪律: 都要独立验证, 都不接受「应该有吧」; 也呼应前篇验证一节的口径: 安全修复的验收, 不能停在「代码看起来对」。本批的条款登记一并在此: 输出面净化升级为全输出面单源 (OF-14), 写入前配置路径锚点检查 (BC-40), 设备边界 (BC-41 / OF-15), rm 阶段 ENOENT 分桶复核 (EC-07), 三入口解析面排除当前目录 (EC-08); du 探针的 win32 守卫与既有 EC-03 对齐。
