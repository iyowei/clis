`sweep-node-modules` 干的事很朴素: 在工作区里找散落的 `node_modules`, 量出体积, 删掉。围绕「删」这个动作, 它建了一套相当克制的纪律: 预览默认、`--yes` 才动手, 动手前每个目标还要过一组不变量 (末段恰为 `node_modules`、位于声明的扫描根之下、不是文件系统根与家目录本体、去重后无重复、根锚点链逐级须为真目录)。

这些闸防的是同一件事: 删错地方。而 2026-09-24 这次加固补上的, 是两个此前没人问过的问题: 删对了地方, 东西还能不能回来; 要删的地方, 还是不是原来那个。

> 删除的合法性其实有两半: 位置合法, 加上可恢复。这次加固的两处修补, 恰好分落两半: 可恢复的一半, 此前只是一条未经检验的假设; 位置合法的一半, 参照点从没被人核对过。

这篇文档把两处问题都按同一条线讲: 怎么形成的、为什么严重、怎么修的。它不复述条款 (那是[删除安全闸](deletion-guard.md) 的事), 只讲这些条款为什么长成现在这样。

## 删除的合法性, 一半建立在「可恢复」之上

要弄清这次加固动了什么, 得先回到这个工具的删除模型。

模型写在 [ADR 0002](../../packages/sweep-node-modules/docs/adrs/0002-fixed-config-and-preview-execution.md) 里: 判定用固定配置, 执行用「预览默认, `--yes` 才删」。它的合法性论证落在一句话上: 排除名单漏维护的后果, 是「被清项目的 `node_modules` 需要重装」(可恢复, 非数据损失)。

这句话是整个删除动作的地基。翻译成操作层的话: 删一个项目依赖, 相当于扔掉一份复印件; 原件 (项目里的 `package.json` 与锁文件) 还在原地, 一句 `npm install` 就能再印一份。删除之所以可以大胆, 是因为删掉的从来不是唯一的那一份。

不变量守的是这套论证的边界: 确保被删的确实是某个扫描根之下、名为 `node_modules` 的目录, 不多碰一个字符。但它脚下的地基是「删掉的东西装得回来」, 而这块地基从写下那天起, 只被拿到一种目标上检验过: 用户项目自己的依赖。

直到有人把扫描根设成家目录, 拿它去碰第二种目标。

## 另一类 node_modules, 名字叫安装树

家目录里除了项目, 还住着另一类 `node_modules`: 包管理器、版本管理器、编辑器插件为「它们自己」装的依赖。这类目录有个名字: 安装树 (install tree)。

它们与项目依赖的区别不在形态 (都叫 `node_modules`, 都躺在某层目录之下), 在恢复性: 项目依赖删了, 重装即回; 安装树的很多目录删了, 没有「重装」这个动作可做, 因为它的清单本身就是数据, 而且往往只此一份。

2026-09-24 的安全审计把这个问题确证了出来, 随后在本机实测: 以家目录为根、深度四层以内, 盘出 92 处 `node_modules` (另一轮盘点记 97 处)。其中这几处的性质, 与列表上的其他条目完全不同:

| 目标                                  | 规模                                            |
| ------------------------------------- | ----------------------------------------------- |
| `~/.bun/install/global/node_modules`  | 1627 个包, 4.1 至 4.25 GB; 本工具自身也装于其中 |
| fnm 各 node 版本的 `lib/node_modules` | 12 个版本各一份; 用户全局包清单的唯一所在       |
| `~/.vscode/extensions/*/node_modules` | 28 处, 编辑器扩展自带的依赖                     |
| `~/.npm/_npx/*/node_modules`          | 26 处, npx 的包缓存                             |

规模最小的两类删掉只是麻烦: 重装扩展、重新下载缓存。不可逆落在前两类, 尤其版本管理器那一类: fnm 的 `<版本目录>/lib/node_modules` 是用户全局包清单的唯一所在, 装过哪些全局工具, 只在这里记着。删掉之后, 「重装」无处可做。重新安装一个 node 版本, 官方只带回 npm 与 corepack; 用户装过的全局工具就此永久丢失。

至于 `~/.bun` 那棵树, 还有一处安静的巧合: 本工具自己就是那 1627 个包中的一个, `~/.bun/bin/sweep-nm` 指向的入口文件就躺在里面。清单上有一行, 是它自己。

一句话: 项目依赖是复印件, 安装树里的很多目录是原件本身; ADR 0002 那句「可恢复, 非数据损失」, 在这类目标上不成立。

## 问题怎么滑过所有防线

回头看, 这个风险不是某个组件的错误, 而是几个各自正确的设计叠加出的盲区。

默认根是第一个环节, 它本身有道理: 向导把扫描根默认设为家目录 (非交互环境回退到当前目录), 一路回车即可拿到这个默认值。家目录是工作区与项目的常见落点, 拿它当默认不算错。麻烦在于 `~/.bun`、`~/.npm`、`~/.vscode` 这些安装树同样是家目录的常住居民, 默认根一落地, 它们全部进了扫描范围。

接着是删除闸。安全闸判的是「路径末段是否恰为 `node_modules`、是否在根之下」, 而安装树全部满足: 它确实叫 `node_modules`, 也确实在根之下。那道闸像一位只认门牌的搬家工: 门牌上写着「清理目标」, 他就动手搬, 不区分这间屋里放的是客房备品, 还是整栋楼的配电房。

再往下是预览。清单渲染有一条规格: 路径末尾的 `/node_modules` 是每行恒定的后缀, 与左侧的项目名重复, 属噪声, 剥掉。这条规格对项目行是对的; 对安装树行, 它剥掉的恰恰是唯一的类别线索。`~/.bun/install/global` 摆在清单上, 看起来就是一个普通目录。加上清单逐行同形 (一行一条, 路径加体积), 92 行里没有任何一行提示「这里是安装树」。

剩下的是时序: 向导写入配置的那一轮强制预览 (「看清再删」在首次使用路径上的落地) 之后, 下一次运行 `sweep-nm --yes` 即执行删除, 名单未变, 不设再确认。预览机制的全部价值建立在「清单看得清」上, 而在这批目标上, 这个前提恰好不成立。

## 第一道防线: 默认排除名单

修法一改的是配置的默认值: `exclude` 字段缺省时不再为空, 而是取一份内置保守名单, 20 个目录名分三组:

| 分组                  | 目录名                                                                        |
| --------------------- | ----------------------------------------------------------------------------- |
| 包管理器 / 版本管理器 | `.bun` `.npm` `.pnpm-store` `.yarn` `.nvm` `nvm` `.fnm` `.volta` `.asdf` `.n` |
| 编辑器 / IDE          | `.vscode` `.vscode-insiders` `.vscode-server` `.cursor` `.antigravity`        |
| 系统 / 应用数据根     | `Library` `.local` `.config` `.cache` `.claude`                               |

语义与用户自己写的名单完全一致: 任意一级目录名命中即跳过; 变的是默认值从空名单变成这 20 个名字。

它不是什么, 值得说明白: 它不是新的检查环节, 也不是权限。安装树还原样待在磁盘上, 没人碰它; 名单的作用点在扫描阶段, 遍历到这些目录门口就不进去, 它们的 `node_modules` 连清单都上不了。缺了它会怎样? 以家目录为根时, 高危目标会整批出现在清单上, 直接暴露在删除批面前, 而删除批的下一站, 就是不可逆。

覆盖规则照旧例: 用户在配置文件里显式写出 `exclude` (哪怕写成空数组), 就完全以用户的名单为准, 默认名单不参与。想「默认之外再加」, 在名单里带上默认项即可。这是「判定依据是显式文件」这条老性格的自然延伸, 不因加固而改。

有一个静默规则要单独交代: 内置名单里的名字, 本次扫描零命中时不告警。理由很实际: 名单依平台与用户环境而异 (Linux 上根本没有 `Library`), 逐项告警必然刷屏, 用户也无从「修正」。这必须与另一种情况分开: 用户手写名字拼错是输入错误, 必须响 (保命名单不得静默失效; 默认名单项的豁免记在 `BC-09`)。

## 第二道防线: 语义闸与 `--force`

名单挡掉绝大多数, 但它是一份枚举, 枚举有边界。三类漏网必须有人接住: 用户显式写出 `exclude` 覆盖掉默认名单 (覆盖是既定权利, 不能拿默认值兜底); 形态不在名单里的应用私有树 (本机实测确有: `~/.oh-my-opencode` 237 MB、`~/.stepfun/releases/deps-6` 51 MB、`~/.jcode/skills/archify`, 这批名字无法穷举); 还有将来, 明天冒出一个新工具, 把安装树栽在别处, 名单永远赶不上。

于是有了第二道防线: 新增一个纯路径判定 (`classify.ts`), 把它看到的每个目标分成两类: 项目依赖, 或疑似安装树。判定三级, 逐条短路:

1. `node_modules` 之上任一级目录名命中安装树容器名 (默认排除名单, 再加 `extensions` 与 `_npx` 两个只在形态上有意义的容器段);
2. `node_modules` 的父目录名为 `lib` (fnm / nvm / volta / asdf 的全局包一律落在 `<版本目录>/lib/node_modules`);
3. `node_modules` 位于家目录下的隐藏目录里 (应用私有根的惯例落点, 兜住名字穷举不出来的那批)。

命中的判为疑似, 其余按项目依赖处置。这里有一个刻意的取舍: 判定只看路径形态, 不看目录内容。读内容能把判定做得更准, 但会把判定与磁盘状态耦合 (竞态、权限噪声), 也越过纯函数边界; 形态判定的代价是误判, 而误判的方向会被保守取向兜住。

一句话概括两道闸的分工: 第一道按名字拦, 第二道按形态拦。名字是枚举, 形态是兜底。

疑似目标的行事方式分三面:

- 预览面: 路径保留 `node_modules` 后缀 (剥掉后缀会把安装树显示成项目, 后缀在这里是唯一的类别线索), 行尾标注判定理由 (如「疑似安装树: 位于 .bun 安装树目录」), 清单末行给出跳过计数;
- 删除面: 默认不进删除批。执行模式下按「未处理」呈现 (行尾「已跳过 (加 `--force` 一并清理)」, 退出码 1); 它从未进入删除批, 与「删除失败」是两回事;
- 放行通道: `--force` 显式放行, 疑似目标照常进入删除批。

还有一条关键性质: 这道闸不受用户配置影响。用户把默认排除项从配置里删掉, 扫描面少了名单的保护, 但删除批的门口, 这道闸仍然站着。它判的是形态, 不是名字, 用户怎么改名单都不影响它。

## 保守的代价, 与 `--force` 的边界

形态判定会误判, 这笔代价登记在设计文档里, 也该在这篇里说清: monorepo 里真有一个名叫 `lib` 的包 (`packages/lib/node_modules`)、一个名叫 `extensions` 的容器, 或者一个刻意藏进点目录的项目 (`~/.my-project/node_modules`), 都会被判成疑似, 要清理就得加 `--force`。判定只看路径不看内容, 这类同名误伤避不开; 家目录本体自己的 `node_modules` 不受影响, 它仍按项目判 (家目录本身可以就是一个工作区)。

代价可以接受, 是因为两个方向的损失不对称: 误判的代价是加一次 `--force`, 一个小麻烦, 可逆; 漏判的代价是把真安装树当项目删掉, 不可逆。判定方向必须落在安全侧, 这不是一句口号, 是拿两类损失的量级差换来的。

`--force` 的边界同样要说清: 它只影响删除批次的构造, 把疑似目标收进批次; 安全闸的不变量照旧全部执行, 预览的零副作用语义也不变。它是一个需要显式说出口的口令, 不是「关掉安全」的开关。

两道防线到此合起来看: 名单在扫描阶段按名字挡掉绝大多数; 语义闸在删除批门口按形态接住漏网的。名字集合与形态判据来源不同, 漏过前者的大概率被后者接住; 两边都漏的, 就是上面说的那些误判面, 代价落在「多问一次」这一侧。

## 另一半的盲区: 那个没人核对的根

两道防线管的全是「删什么」。回到开头那句话的另一半: 位置合法。

这半看起来滴水不漏: 目标要过一组不变量, 删除前还有一套逐级复核, 从根一路 `lstat` 到目标的父目录, 任何一级被掉包 (换成符号链接、换成非目录) 都整批中止。

可这些判定判的都是同一件事: 目标相对「根」是否合法。而「根」自己, 配置里写下的那个名字, 此刻还指着当初那个地方吗, 没人核对过。

也不是没检查过它。逐级复核的链条, 第一环就是根, 只不过检查的是 `realpath(root)` 之后的根。拿解析结果做检查是句同义反复: 解析能成功, 本身就意味着「此刻它是个真目录」。而真正要紧的问题, 「配置里写的名字」到「实际指向哪里」这个映射有没有被人改过, 没有任何一步在看。

「目标在根之下」这条同样安静。它比较的两侧都取自真实路径; 根的真身被换掉时, 两侧一起漂移, 比较恒成立。站在那儿的防线, 拦的其实是自己跟自己的影子。

同一次审计里, 这条链也被逐行复核过: 每一步都照着设计在走, 一个 bug 都没有。问题不在某个组件写错, 在于整条防线的前提: 它默认根就是当初那个根。

它像小区快递柜的门卫, 规矩是只放行 3 号柜里的包裹。每单他都没偷懒: 翻过、核对过, 确实在 3 号柜里。可没人核对过 3 号柜本身还是不是原来那个。有人把整个柜子搬走, 原地立一个贴着你名字的假柜, 柜子背后通向别人的仓库, 门卫照样放行。每一单都核对过, 每一单都对。

这样的换位不需要什么身手: 对根或它上一级目录有写权限的第三方就够了, 共享目录里的另一位用户、公用的 CI 机器、容器挂载的共享卷都算。动作两步: 把根改名搬走; 原地放一个符号链接, 指向他选定的树。然后他就可以离场了, 这一次布置持久生效, 受害者下次运行 `sweep-nm --yes`, 删除会开进那棵树; 改动之前, 没有任何一步会拦它。报告写「成功」, 归因指着配置里的原始拼写, 从头到尾, 没有一处会喊。

严重性得单独量一次, 因为项目里登记过一条长得很像的风险: 复核完成到删除动作之间, 有一个可以掉包目标的窗口, 实测不到 1.4 微秒, 判定「现实不可达, 可接受」。那条结论有个前提: 攻击者得守在那条微秒级的缝里抢时间; 而这次这种换位不抢任何时刻, 它发生在你运行之前, 一次布置、离线完成、持久生效。复核链跑得再快也没用, 它一开始看到的, 就已经是假柜子。那条「现实不可达」的量化, 管不到这里。

## 把根钉在拼写上: 第五道不变量与链头判定

修法分两处, 分别落在闸门与删除层。

删除层这头, 先让拼写进得来: 根传进来时, 不再是一个解析后的路径, 而是一对必须同去同回的搭档, 配置里的原始拼写加解析后的真实路径。这一对在类型上绑死, 拆开单用, 编译就不过。然后每条删除前, 对根自身做一次类型判定 (`lstat`, 不跟进末段): 一旦是符号链接, 整批中止, 理由就写「根被替换为符号链接」。

闸门这头, 加的是第五道不变量: 配置里的根 (原始拼写) 及其祖先链 (自根的一级子目录至根自身, 文件系统根本身不入链), 逐级须为真目录; 任一级是符号链接, 该根下的目标一律拒, 整批拒绝, 零删除。拒绝文案给出根与符号链接的定位, 并附上改写指引: 把配置根改写为不含符号链接的真实路径。

两处互为纵深: 闸门把得宽, 判整条锚点链 (根自身加祖先); 删除层把得近, 在每条动手前只判链头 (根自身), 祖先链被换的场景由闸门那道不变量接住。这与既有的分层同构 (不变量在闸门层, 逐级复核在删除层), 等于给同一个信任锚加了两道不同时机的检查。

判据为什么非落在拼写上, 值得单独说。真实路径只会报告「此刻解析到了哪」, 名字到指向这个映射什么时候被动过, 它一个字都不会说; 拼写形态是唯一还留着证据的地方。拿证据判, 拿结论判不了。

## 同一个链接: 扫描跟进, 删除拒绝

项目里早有一条契约 (`BC-11`): 配置根自身是个符号链接时, 扫描照常跟进, 理由是「显式即授权」, 链接是用户自己写下的, 预览又只读, 跟进去没有风险。这次的新规管的是删除侧信任锚: 不可逆动作凭什么信这个根。于是同一份配置、同一个链接, 两边的答案从此不同: 预览照常出清单 (退出码 0), `--yes` 整批拒绝 (退出码 1)。

这不是新规与旧约打架, 是有意的分叉, 理由一句话: 门槛该跟着可逆性走。只读的扫描可以宽, 跟进一个链接, 最坏不过是清单多几行少几行; 不可逆的删除必须严, 判错一次, 东西回不来。而且删除侧还多一层苦衷: 这个链接是用户当初亲手写下的, 还是后来被人换上的, 两种可能长得一模一样, 判不出来。宽的那边容得下错, 严的这边赌不起。

同一句「判不出来路」, 在 macOS 上还给诚实用户开出一笔账: 配置根写在 `/tmp`、`/var` 这类路径下会被拒。原因是系统固有的符号链接 (比如 `/var` 指向 `/private/var`) 与攻击者的换位, 在拼写层无从区分; 区分不了, 就一并保守拒绝, 拒绝文案自带改写指引: 改写为 `/private/...` 形态的真实路径即可放行。要不要给「系统固有链接」开白名单? 想过, 不做: 白名单按名字挑, 同一个命名方式就能把它绕过去; 何况那意味着又一份要维护、会过期的名单。

这笔账记在明处: 严格有代价, 代价是让一部分诚实路径多改一次拼写; 换来的是一条不需要鉴别的规矩: 判不了来路的, 一律不放行。

## 还没关上的那几处

修法的覆盖范围要说尽, 免得它显得比实际更周全。

它关住的是「链接介入」这一种载体: 名字还在原地, 但名字到指向的映射被换成了一条符号链接。同型的换位如果换的是真目录, `lstat` 看不出真目录与真目录的差别, 仍在不可识别之列。这一类会把危害落在「假成功」这一面: 删的不是当初那一个, 报告却写成功; 而这一面此前另有兜底, 复核发现组件半路消失时, 宁可要求复查, 也不报成功。

还有一笔旧账维持原状: 复核与删除之间那个微秒级的窗口, 依旧开着, 没有因这次修法变大或变小。这两处连同各自的量化登记, 都在[删除安全闸](deletion-guard.md) 的残余风险一节里。

## 验证: 五道闸门, 加两次实跑复验

安全修复的验收不能停在「代码看起来对」。

先看既有闸门: 单元测试、转写契约套件 (双载体)、类型检查、lint、格式检查, 五道闸门全部通过 (条目数以实时输出为准)。行为契约同步登记了新条款: `BC-36` 默认排除名单、`BC-37` 目标类别判定、`BC-38` 疑似目标默认跳过与 `--force` 放行, 以及根锚点检查的 `BC-39` (与 `BC-11` 的扫描 / 删除分工写在其中); 语料的期望按条款原文可辩护, 不靠「跑一遍记下来」式捕获。既有语料逐字未动, 尤其扫描侧的 `scan-root-symlink-followed` 实跑仍绿: 分叉是预期行为, 不是新旧条款打架。

再拿真实的高危输入试一遍: 以家目录为根, 只读实跑预览 (全程未动用 `--yes`)。结果: 每个高危目标要么根本没进清单 (被默认名单挡在扫描之外), 要么带着标记出现在清单上、被划入跳过侧 (被语义闸接住)。

根锚点这道防线也拿真实场景演了一遍: 正常根下 `--yes` 删除成功 (退出码 0); 把根换成指向另一棵树的符号链接, 同一份配置再上 `--yes`, 整批拒绝 (退出码 1), 攻击者那棵树完好; 同一份配置走预览, 照常出清单 (退出码 0); 把配置写成不含符号链接的真实路径, 删除恢复可用 (退出码 0)。

到这里可以给这次加固一个准确的结论: 此前那批「删了回不来」的目标, 现在要么进不了场, 要么在删除批门口被拦下, 放行的钥匙 `--force`, 必须有人显式交出; 而那个被掉包的根, 在拼写上就会被认出来, 一步都迈不出去。

回到开头那个判断: 删除的合法性有两半。位置合法, 这次补的是它的起点: 拿拼写判根; 可恢复, 在这次之前只是一条隐含假设, 而假设是不大经得起检验的东西。

现在的结构是: 名字层面有名单, 形态层面有语义闸, 起点层面有锚点链的逐级核对; 之外留一道显式的 `--force`。这套结构不自称完备 (误判面写在纸上, 就是为了提醒这一点), 它承诺的只有一件事: 在不可逆的删除动作前, 把两个问题都问完 (这个目标删了回得来吗, 这个根还是原来那个吗); 看不准的时候, 默认不删。

还有一个安静的注脚。本工具自己就住在 `~/.bun/install/global/node_modules` 里, 而现在护着它的防线, 与护着所有安装树的防线是同一份: 那棵树默认连清单都进不来。一个清理工具最体面的自卫方式, 大概就是把自己也关在门外。
