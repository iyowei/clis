# 依赖方向纪律 (Dependency Direction)

> 文档类型: 仓库级设计
> 适用对象: 本仓维护者与 AI Agent
> 前置: [包分类与发布协议](package-classification.md)

## 契约

集合内各包之间的依赖构成**有向无环图**, 且方向受限:

| 允许                  | 说明                                                    |
| --------------------- | ------------------------------------------------------- |
| CLI 工具 → 公开库     | 常规分层: 工具使用库                                    |
| CLI 工具 → 仓内私有库 | 同上                                                    |
| 公开库 → 公开库       | 允许, 但保持浅 (深度 ≤ 2); 出现更深的链条, 先提炼中间层 |
| 仓内私有库 → 公开库   | 允许                                                    |

**禁止**:

- 公开库 → CLI 工具 (库不得反向依赖工具);
- 仓内私有库 → CLI 工具 (同上);
- CLI 工具 ↔ CLI 工具 (工具之间禁止互相依赖, 出现共享需求时把共享部分**抽成一个库**)。

规则对 `dependencies` 与 `devDependencies` 一视同仁: 测试期的跨工具引用同样禁止。

## 理由

- **独立发布**: 工具与库按各自的提交记录判定版本发布 (multi-release 按包独立); 反向依赖会让工具的发布被库的发布节奏绑架;
- **独立回滚**: 每个包的改动可单独回退, 不牵动其他包的历史;
- **脚手架可裁剪**: 生成新项目时按档裁剪包, 方向单一的依赖图裁剪后仍自洽 (见[能力分档](capability-tiers.md));
- **认知负担**: 单向依赖让「谁可以动、动了影响谁」一看便知。

## 执行 (规划)

在本仓实现一道**依赖方向闸门**: 扫描各包 `package.json` 的 workspace 依赖 (含 devDependencies), 对照上表核对方向; 违规就亮红灯。与现有四道闸门同属一类, 挂进统一闸门链 (挂载方式见[能力分档](capability-tiers.md)的裁剪点约定)。

## 例外

破例必须先在[技术债登记](tech-debt.md)记一笔 (含理由与解除条件), 再引入依赖; 无登记的破例视为违规。
