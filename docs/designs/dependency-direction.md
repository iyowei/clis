# 依赖方向纪律 (Dependency Direction)

> 文档类型: 仓库级设计
> 适用对象: 本仓维护者与 AI Agent
> 前置: [包分类与发布协议](package-classification.md)

## 契约

集合内的包间依赖构成**有向无环图**, 且方向受限:

| 允许                  | 说明                                                  |
| --------------------- | ----------------------------------------------------- |
| CLI 工具 → 公开库     | 常规分层: 工具是库的消费方                            |
| CLI 工具 → 仓内私有库 | 同上                                                  |
| 公开库 → 公开库       | 允许, 但保持浅 (深度 ≤ 2); 出现更深的链条先提炼中间层 |
| 仓内私有库 → 公开库   | 允许                                                  |

**禁止**:

- 公开库 → CLI 工具 (库不得反向依赖工具);
- 仓内私有库 → CLI 工具 (同上);
- CLI 工具 ↔ CLI 工具 (工具之间禁止互依, 出现共享需求时把共享部分**下沉为库**)。

规则对 `dependencies` 与 `devDependencies` 同权: 测试期的跨工具引用同样受禁。

## 理由

- **独立发布**: 工具与库各自按自己的提交判版本发布 (multi-release 按包独立); 反向依赖会让工具的发布被库的发布节奏绑架;
- **独立回滚**: 每个成员的改动可单独回退, 不牵动其他成员的历史;
- **脚手架可裁剪**: 生成新项目时按档裁剪包集, 方向单一的图裁剪后仍自洽 (见[装置分档](capability-tiers.md));
- **认知负担**: 单向依赖让「谁可以动、动了影响谁」一眼可答。

## 执行 (规划)

落地为本仓的**依赖方向闸门**: 扫描各包 `package.json` 的 workspace 依赖 (含 devDependencies), 对照上表断言方向; 违规即红灯。与既有四闸门同族, 挂入统一闸门链 (挂载方式见[能力分档](capability-tiers.md)的裁剪点约定)。

## 例外

破例须先在[技术债登记](tech-debt.md)记一笔 (含理由与解除条件), 再落依赖; 无登记的破例视为违规。
