# 转写实施纪律 (全仓通用 · 语言无关)

> 用途: 把任意包的 TypeScript 参考实现, 按「包级行为契约 + 全量金样本语料 + 确定性验收器 + 差分模糊测试」转写到目标语言时, 约束实施者 (AI 或人) 的行为。
>
> 本文件不承载任何具体产品的业务规格: 业务规格全量在目标包的 `packages/<pkg>/docs/protocol/` 中。本文件只回答「怎么实施、怎么验收、哪些红线绝不能碰」。

## 一、角色边界

你是实施者, 不是设计者, 不是优化者。

- 逐条实现契约条款; 行为面一切以包级行为契约为准。
- 「更合理 / 更优雅 / 更高效」的改动, 只要改变可观察行为, 一律不做。
- 可观察行为面有两个, 都要等价:
  1. **CLI 面**: `argv / env / stdin / cwd` -> `stdout / stderr / 退出码 / 文件系统效果`;
  2. **API 面**: 按包级 API harness 协议提供的 harness 可执行, 经调用指令 -> `返回值 / 抛错码 / 事件流 / 文件系统效果`。
- 「等价」= 两个面上均与参考实现逐字节 / 逐值一致。内部模块划分与语言惯用风格不作要求, 但绝不构成偏离契约的借口。

## 二、反敷衍三条硬红线

在规模化转写中, 最致命的风险不是编译报错, 而是「编译过了但逻辑是假的」。以下三类行为一经出现直接判为**阻断缺陷**, 必须推倒重写:

1. **严禁空壳 stub 凑编译**: 不得为让类型检查或链接通过, 留下 `todo!()`、`unimplemented!()`、空函数体、假返回值或硬编码固定答案。条款未覆盖处必须记入缺口清单并显式上报, 严禁静默留壳。
2. **严禁写长段注释为 workaround 辩解**: 当你发现需要写好几行注释来解释「为什么这里跟原实现不一样、为什么暂时这样绕过也行」时, 立刻停手。需要辩解的 workaround 说明当前设计与契约冲突, 必须正面修代码, 而不是用注释说服评审者。
3. **严禁缩水占位常量**: 不得把并发上限、参数预算、缓冲区大小、重试次数、路径长度护栏、默认排除列表等关键常量临时调小或截断 (例如把上限 32 改成 4、把 32 项护栏删成 3 项) 以后「再改回来」。常量与边界值从第一版就必须与契约逐项对齐。

## 三、实施硬纪律

1. **动工前先建映射表 (`PORTING_MAP.tsv`)**: 全量转写前先列清源文件、目标文件、关联条款编号与状态, 逐条推进并实时回填。交付完成定义不是「代码写完」, 而是「映射表无空行 + 验收器双面全绿 + 差分模糊零差异」。
2. **3 文件试跑闸门 (`Trial Run`)**: 禁止第一轮就一次性铺开转写整个代码库。先挑选 **3 个具代表性的核心文件** (建议组合: 1 个纯函数/格式化模块 + 1 个校验/解析模块 + 1 个文件系统/平台 IO 模块), 完整走通「转写 -> 独立对抗评审 -> 修复 -> 编译与单测通过 -> 接口契合度复核」。试跑过关、确认模块边界与错误类型设计无误后, 再全面铺开。
3. **1 实现者 + 2 对抗评审者 + 1 修复者**: 每完成一个逻辑波次, 必须拉起独立干净上下文的对抗评审者 (详见 [`adversarial-reviewer.md`](adversarial-reviewer.md) 与 [`ts-porting-pitfalls.md`](ts-porting-pitfalls.md)) 做只读审查:
   - 评审者 A 专盯「行为契约逐条等价性 + TS 形似神异语义暗差」;
   - 评审者 B 专盯「反敷衍三条红线 + 错误路径/平台分支/内存与资源清理」;
   - 评审者不直接改代码, 只输出带证据的阻断项; 修复者按阻断清单逐项根治。
4. **规格未覆盖处停手报缺口, 不发明**: 契约没写、语料没覆盖、而实现必须做决定的地方, 记入缺口清单 (位置 + 疑问 + 关联条款), 继续其余部分; 严禁猜测、严禁把「参考实现碰巧这么做」当规格。
5. **只许等价, 不许附加**: 不添加契约之外的 `stdout / stderr` 输出 (额外提示语、日志、进度), 不额外读写文件, 不改退出码语义, 不多删或少删一个字节。
6. **不动套件件**: 契约 / 语料 / 覆盖表 / 验收器一律只读。发现套件内部矛盾或错漏时报缺口等裁决, 严禁改语料或跳过用例迁就实现。
7. **失败先定责, 借诊断单闭环**: 验收失败时, 用 `--emit-failures <dir>` 导出按用例拆分的自包含 Markdown 诊断单 (内含条款原文、语料 JSON、失败差异与原始输出), 逐条定责 (实现缺陷 / 契约缺漏 / 语料错误), 严禁拿整屏大日志盲猜乱改。
8. **强制 `release` 产物双面全量终验 (`0 skipped`)**:
   - 最终验收**必须**运行在优化后的 `release` 交付产物上 (而非 `debug` 构建: `debug` 与 `release` 在断言求值、溢出行为、性能与时序上均可能存在实质差异);
   - 禁止拿 `--filter` 子集运行充当全绿证明: 交付验收报告必须显示全集实跑、跳过数为 `0` (`fullRunVerified: true`), 且连续跑满 **3 次**结果完全一致;
   - 同步跑通包级 `fuzz-targets.json` 的差分模糊测试 (`run-diff-fuzz.ts`), 目标 harness 与参考实现零差异、零崩溃。
9. **环境相关路径如实实施**: 降级路径 (无 TTY / `NO_COLOR` / 平台差异 / 外部命令缺失) 必须按契约如实实施, 不得因「本机跑不到」而省略。
10. **并行转写工程纪律**: 多代理并行转写互不交叉的模块时:
    - 批量写盘阶段禁止在共享工作树内执行 `git stash`、`git reset` 或 `git checkout -- .` 等破坏性全局操作;
    - 批量翻译期间按波次统一编译检查, 避免每个微小编辑都触发一次全量重编与锁竞争。

## 四、交付物清单 (四件缺一不可)

1. **映射台账 (`PORTING_MAP.tsv`)**: 每条契约条款与每个源模块对应到目标代码路径与函数名; 未实施或存疑条目显式标注。
2. **缺口清单**: 每条含位置、疑问、关联条款、影响面与已补原生单测坐标; 无缺口也要显式声明「无」。
3. **双面 `release` 验收报告原文**: CLI target 与 API harness target 的完整运行命令 + 全量原始输出 (须含全集计数、`跳过 0`、连续 3 次一致)。严禁摘要代原文、严禁带 `--filter` 交差。
4. **差分模糊测试报告原文**: `run-diff-fuzz.ts` 完整运行命令 (含 `--seed` 与 `--cases`) 与零差异原始输出。
