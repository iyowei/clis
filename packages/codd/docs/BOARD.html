三组服务各干什么

  • mongo: 数据库本体 (tcmalloc-google + /dev/tcp 零 V8 尖峰探针), 首次自建 756B 400 权限密钥
  • mongo-init: 等 healthy 后跑幂等 init.js (切主后自动路由活跃主节点), 配完退出 exit=0
  • mongo-tools: 按需启停的 Bun + mongodump + 沙箱 mongod 容器, 宿主机免装任何工具
安全 多库隔离 · 纯字母数字

多库与三账号隔离

  • 业务账号 (app): 主库配专属 readWrite; 在 deploy.json 的 apps[] 追加多库即可由生成器自动配权与生成随机口令
  • 备份账号 (backup): 仅 admin.backup 只读角色, 兼管从节点热备与容器内沙箱 drill 索引比对
  • 管理员 (root): 仅限 init 与紧急真恢复 restore
所有路径、卷、网络与定时任务全部自动嵌入唯一 FINGERPRINT, 同机部署两个同名实例只需错开 port 即 100% 零冲突。

资源与公式 4

2G 起步 WT 缓存 0.5GB
8G 生产 WT 缓存 3.5GB
官方余量公式 0.5 × (RAM-1G)
ADR 0012 · 0015 rs0 · oplog >= 990MB

为什么默认全员副本集

Standalone 无法用多文档事务和 Change Streams, 故单机直接启 rs0; 同机多业务靠同实例分库隔离 (apps[] / MONGO_EXTRA_APPS), 硬塞 3 容器既 3 倍耗费内存磁盘又无硬件容灾。真三物理节点看右侧「多副本 · Podman」列。

oplog 是磁盘上限 (保底 990MB 按盘比例计算); WT 是内存上限, 平时按需占用。详见 ADR 0012 与 ADR 0015。

Step 4 · 五步验收

目标服务器 写 1 条探测文档避开空库报错, 验证主节点、工具构建、备份及沙箱演练全链路后再清理: 

# [执行设备: 目标服务器]
set -a && . ./.env && set +a
C="${STACK_PREFIX}-${FINGERPRINT}"
ROOT_AUTH="${MONGO_INITDB_ROOT_USERNAME}:${MONGO_INITDB_ROOT_PASSWORD}"
APP_AUTH="${MONGO_APP_USER}:${MONGO_APP_PASSWORD}"
HOST_QS="127.0.0.1:${MONGO_PORT:-27117}"

# 1) 确认 PRIMARY 与版本号
podman exec "$C" mongosh \
  "mongodb://${ROOT_AUTH}@${HOST_QS}/admin?authSource=admin&directConnection=true" \
  --quiet \
  --eval 'printjson({
    primary: db.hello().isWritablePrimary,
    state: rs.status().members[0].stateStr,
    version: db.version()
  })'

# 2) 业务账号写探测文档 (使库非空)
APP_URI="mongodb://${APP_AUTH}@${HOST_QS}/${MONGO_APP_DATABASE}?authSource=${MONGO_APP_DATABASE}&directConnection=true"
podman exec "$C" mongosh \
  "$APP_URI" \
  --quiet \
  --eval '
    db.__deploy_smoke.insertOne({
      ok: true,
      at: new Date()
    });
    print(
      "count:",
      db.__deploy_smoke.countDocuments({})
    );
  '

# 3) 首次备份 + 4) 临时库演练
make backup \
  && make drill

# 5) 清理临时探测集合
podman exec "$C" mongosh \
  "$APP_URI" \
  --quiet \
  --eval 'db.__deploy_smoke.drop()'

多副本 · Podman 5

3 物理节点 PSS · 差异 .env

何时用真 3 节点

面向 3 台独立物理机 (node1 / node2 / node3) 防单台掉电坏盘。三机共用同一套 template/podman/ 模板, 靠 codd 一次导出 3 个对称节点包。

默认用 27117 端口 (自定义 port 时放行实际端口号), 防火墙只向三节点与内网放行 (Linux ufw/firewalld; macOS 放行 gvproxy)。详版见 podman-replica-set.md。
Step 1 · 一次生成 3 节点并同步

本地开发机 配置 mode: "replica-set" 填 3 台 nodes, 一次生成共用指纹与 MONGO_KEYFILE 的三个节点包并分别推上服务器。 

# [执行设备: 本地开发机] 1) 在部署配置所在目录直接指定清单文件生成 3 个现成节点包
codd deploy.ha.json

# [执行设备: 本地开发机] 2) 将 3 个带唯一指纹的独立目录分别推往对应物理服务器
rsync -av dist/mongo-ha-<fp>-node1/ ops@10.8.0.11:~/srv/stacks/mongo-ha-<fp>-node1/
rsync -av dist/mongo-ha-<fp>-node2/ ops@10.8.0.12:~/srv/stacks/mongo-ha-<fp>-node2/
rsync -av dist/mongo-ha-<fp>-node3/ ops@10.8.0.13:~/srv/stacks/mongo-ha-<fp>-node3/
Step 2 · 先启 2 台从节点

从服务器 node2·3 分别登录两台从机启动预设 RS_ROLE=secondary 的节点包, 保持空盘等待主节点同步。 

# 生成器已自动写好每台差异项 (示例 node2; node3 同理, 三机资源参数完全一致):
#   MONGO_BIND_IP=10.8.0.12  RS_ROLE=secondary  RS_SELF_HOST=node2
#   RS_MEMBERS=node1:27117,node2:27117,node3:27117
#   RS_PEER_1=node1:10.8.0.11  RS_PEER_2=node3:10.8.0.13

# [执行设备: 分别登录从服务器 node2 与 node3]
cd ~/srv/stacks/mongo-ha-<fp>-node2   # node3 上进入 mongo-ha-<fp>-node3
make tune-host \
  && make check-env \
  && make up \
  && make status
Step 3 · 主节点启动初始化

主服务器 node1 登录 node1 启动 (预设 RS_ROLE=primary), mongo-init 自动完成 3 成员组网与全库建号。 

# node1 已预设主引导参数 (与从节点共享指纹、keyFile 及对等资源上限):
#   MONGO_BIND_IP=10.8.0.11  RS_ROLE=primary  RS_SELF_HOST=node1
#   RS_PEER_1=node2:10.8.0.12  RS_PEER_2=node3:10.8.0.13

# [执行设备: 登录主服务器 node1] 启动后自动发起 rs.initiate 与全库账号初始化
cd ~/srv/stacks/mongo-ha-<fp>-node1
make tune-host \
  && make check-env \
  && make up \
  && make logs
Step 4 · 验收与不停服维护

主服务器 node1 1 台主库写、2 台从库同步; 业务写全三台地址且禁加 directConnection, 重启主库前先喊一声交接班。

  • 怎么看同步成功: 查成员状态是 1 PRIMARY + 2 SECONDARY、全部 health: 1 且落后秒数趋近 0s
  • 怎么连才会自动切换: 写全 node1,node2,node3 就像记 3 个分店电话, 一台断线驱动自动换下一台
  • 备份 / 演练 / 恢复在哪台跑: make backup 自动从 SECONDARY 热备; make drill 走容器内沙箱零污染; 切主后任意节点跑 restore / init 均自动路由新主
  • 不停服重启怎么操作: 先逐台重启 node2、node3; 轮到原主 node1 前先跑 rs.stepDown(60) 退居二线 60 秒让新主接班后再关机 
# [执行设备: 主服务器 node1] 1) 一键检查三机角色与同步延迟
# 成功标志: 1 个 PRIMARY + 2 个 SECONDARY, 全 health=1, 延迟约 0s
cd ~/srv/stacks/mongo-ha-<fp>-node1 && set -a && . ./.env && set +a
C="${STACK_PREFIX}-${FINGERPRINT}"
URI="mongodb://${MONGO_INITDB_ROOT_USERNAME}:${MONGO_INITDB_ROOT_PASSWORD}@127.0.0.1:${MONGO_PORT:-27117}/admin?authSource=admin&directConnection=true"

podman exec "$C" mongosh "$URI" --quiet --eval '
  printjson(rs.status().members.map((m) => ({
    name: m.name, state: m.stateStr, health: m.health
  })));
  rs.printSecondaryReplicationInfo();
'

# 2) 业务端高可用连接串 (写全三台, 禁加 directConnection=true)
# mongodb://<USER>:<PWD>@node1:27117,node2:27117,node3:27117/<DB>?replicaSet=rs0&authSource=<DB>

# 3) 滚动重启不断业务 (先分别对两从机 make down && make up)
# 最后在原主节点喊一句让主 "交接班", 等几秒选出新主后再重启原主机:
podman exec "$C" mongosh "$URI" --quiet --eval 'rs.stepDown(60)'

K8s 单副本部署 5

Helm · 1 Pod rs0 · 27117

何时用 K8s 单副本

用 template/helm/ 轻量运行 1 副本 StatefulSet + PVC, 由科学公式注入限额/缓存/连接数/oplog, init-job 建 rs0 与 extraApps, 默认端口 27117。

支持 codd (mode: "k8s-single") 一键生成 values.generated.yaml 与 deploy.sh。详版见 kubernetes-single.md。
Step 1 · 查集群与建固定 Secret

K8s 管控机 确认存在可用 StorageClass (最好开卷扩容), 手调方式可预建固定 Secret (走生成器可跳至 Step 2)。 

# [执行设备: K8s 管控机 (已配 kubectl 与 helm)] 1) 检查集群连接与存储类
kubectl cluster-info && helm version --short
kubectl get storageclass

# 2) 创建命名空间与独立 Secret (若用生成器 deploy.sh 则会自动创建, 可跳过本段)
NS=data
kubectl create namespace "$NS" --dry-run=client -o yaml | kubectl apply -f -
ROOT_PWD="$(openssl rand -hex 12)"
APP_PWD="$(openssl rand -hex 12)"
BAK_PWD="$(openssl rand -hex 12)"
KEY_B64="$(openssl rand -base64 756 | tr -d '\n')"

kubectl -n "$NS" create secret generic mongo-app-auth \
  --from-literal=root-password="$ROOT_PWD" \
  --from-literal=app-password="$APP_PWD" \
  --from-literal=backup-password="$BAK_PWD" \
  --from-literal=extra-apps="" \
  --from-literal=mongodb-keyfile="$KEY_B64" \
  --dry-run=client -o yaml | kubectl apply -f -
printf 'ROOT=%s\nAPP=%s\nBACKUP=%s\n' "$ROOT_PWD" "$APP_PWD" "$BAK_PWD"
Step 2 · 安装单副本 Release

本地开发机K8s 管控机 开发机生成自带 chart/ 的部署包, 在已配 kubectl 的本机或管控跳板机运行 deploy.sh。 

# 方式 A (推荐): [本地开发机] 生成部署包 -> [K8s 管控机] 执行 deploy.sh
# codd && bash dist/mongo-app-<fp>-k8s/deploy.sh

# 方式 B: [执行设备: K8s 管控机] 手工直调交付包内嵌 ./chart (或仓内 packages/codd/template/helm)
helm upgrade --install mongo-app ./chart \
  --namespace data \
  --set replicaCount=1 \
  --set auth.existingSecret=mongo-app-auth \
  --set service.type=ClusterIP \
  --set config.net.port=27117 \
  --set service.port=27117
Step 3 · 验 Pod 与冒烟写入

K8s 管控机 确认 Pod 为 1/1 Running、init Job 为 Completed, 再进 Pod 验读写与清理探测表。 

# [执行设备: K8s 管控机] 1) 观察 Pod、PVC 与 init Job 状态
kubectl -n data get pods,jobs,pvc -l app.kubernetes.io/instance=mongo-app

# 2) 用业务凭据进 Pod-0 写入 1 条后删除
APP_PWD="$(kubectl -n data get secret mongo-app-auth -o jsonpath='{.data.app-password}' | base64 -d)"
kubectl -n data exec mongo-app-0 -c mongo -- mongosh \
  "mongodb://app:${APP_PWD}@127.0.0.1:27117/app?authSource=app&directConnection=true" \
  --quiet --eval '
    print("primary:", db.hello().isWritablePrimary);
    db.__k8s_smoke.insertOne({ ok: true });
    db.__k8s_smoke.drop();
  '
Step 4 · 连串与 PVC 在线扩容

K8s 管控机 StatefulSet 卷模板不可改, 扩容须在管控机直接 kubectl patch pvc; 同集群业务走内部 Service DNS。 

# [业务配置] 1) 同集群业务 Pod 连接串 (走 ClusterIP Service, 默认端口 27117)
# mongodb://<USER>:<PWD>@mongo-app.data.svc.cluster.local:27117/<DB>?authSource=<DB>&directConnection=true

# [执行设备: K8s 管控机] 2) 在线扩盘 (勿仅改 values.yaml 重跑 upgrade)
kubectl -n data patch pvc data-mongo-app-0 \
  -p '{"spec":{"resources":{"requests":{"storage":"64Gi"}}}}'

接入 RS_MEMBER_HOST

多实例同网防冲突

同一业务容器需要同时挂载多个不同指纹 MongoDB 网络时:

  • 单实例只管一库默认留空; 多实例共网在 deploy.json 开 "multiNetAlias": true, 或设 RS_MEMBER_HOST 为 <prefix>-<FINGERPRINT>:27117
  • 业务连接串主机名同步用容器全名, 避免多个 mongo 服务名互相抢解析

紧急真恢复 · 先 drill 再 restore

目标服务器 从归档文件名解析目标库 <db> 并仅 --nsInclude=<db>.* 单库覆盖恢复, 不动同实例其它库。 

# [执行设备: 目标服务器 部署目录内] 1) 先在独立沙箱演练全部库
make drill

# 2) 按归档文件名识别库名, 确认单库覆盖恢复
make restore \
  FILE=mongo-<db>-YYYYMMDD_HHMMSS.archive.gz \
  CONFIRM=yes
升级 / 扩盘 / 迁卷 · 成对迁移防失钥

目标服务器 迁新指纹必须同时导入 -data 和 -key 密钥卷, 丢失密钥会导致副本集认证失败; macOS VM 扩盘只可调大。 

# [执行设备: 目标服务器 部署目录内] 1) 改 .env MONGO_IMAGE_TAG 后升级 (强制无缓存重建工具镜像)
make up
make tools-rebuild

# 2) 磁盘容量排查与扩容
# [Linux] 无 VM, 直接核查宿主机卷盘余量
df -h ~/.local/share/containers/storage

# [macOS] Podman 虚拟机扩容 (只可调大)
podman machine stop \
  && podman machine set \
    --disk-size 64 \
  && podman machine start

# 3) 迁移旧数据卷与密钥卷到新指纹
podman volume export <旧data> \
  | podman volume import \
    <prefix>-<新fp>-data -

podman volume export <旧key> \
  | podman volume import \
    <prefix>-<新fp>-key -

卡点与文档 5

配置报错 · CHANGE_ME / 非字母数字

.env 未替换模板占位, 或账号密码里带了特殊符号。

优先重跑 codd [--rotate] 重产 .env; 手调场景用 openssl rand -hex 12 重生密码替换后跑 make check-env && make init
空库演练失败 · 无实体集合

make backup 已移除 <100B 阈值 (改为拒绝 0 字节 + verifyGzip 完整解压校验), 但空库在 make drill 恢复后没有任何实体集合仍会报错。

按 Step 4 先写入 1 条临时探测文档即可验通; 正式上线业务写表后即恢复正常
路径 / 端口 · 写不进备份 / 地址占用

macOS 仅 /Users, /private, /var/folders 挂载进 VM (Linux 无此限制); 多实例复用同端口 (默认 27117) 会地址冲突。

统一将 BACKUP_DIR 建在 ~/srv/backups/ 并 mkdir -p; 同机多业务优先用 MONGO_EXTRA_APPS 分库, 独立实例传 ENV=.env.other 换 MONGO_HOST_PORT 与指纹
工具缺失 · podman-compose not found

podman 本体不自带编排引擎, 缺 podman-compose 或 macOS 非交互 SSH 未加载 PATH 时都会报错。

Linux 跑 sudo apt install -y podman-compose (或 sudo dnf install -y podman-compose); macOS 跑 brew install podman-compose 并把 /opt/homebrew/bin 写入 ~/.zshenv (交互登录可另写 ~/.zprofile) 后重跑 make check-env
