# 本质抽象判据与 Rust 可转写边界规范

## 一、四道社区级本质闸门明细

每个候选跨包复用簇只有在全部通过以下 4 道硬门槛时, 才允许立项抽离:

### 闸门 1: 独立产品域复用覆盖门槛

不能单纯按文件夹个数计数:

- **同产品双包去重**: 本仓默认每个产品拆成「API 主包 + CLI 薄壳包」(例如 `@iyowei/codd` 与 `@iyowei/codd-cli`), 两者共用同一产品域 (`domainId`)。仅被同一产品内两个包共用的代码不算跨产品复用, 禁止外抽。
- **按同构职责层衡量**: CLI 薄壳层不应和纯领域 API 主包强绑同一个覆盖基数。按主消费方所属职责层计算该层的独立产品域总数 `D`:
  - `D <= 2`: 必须达到 `2/2` (100%) 全覆盖才抽离;
  - `D === 3`: 必须至少覆盖 `2` 个独立产品域;
  - `D >= 4`: 必须至少覆盖 `3` 个独立产品域。

### 闸门 2: 单一职能本质命题 (拒绝"具象逐物"与垃圾桶包)

1. **剥离具象词测试**: 新包的包名、`description`、导出函数名、错误码与 README 文档中, 严禁出现任何原业务领域词 (`sweep`、`codd`、`mongodb`、`node_modules`、`create-clis` 等)。如果去掉业务词后 API 无法自解释, 说明抽象还停留在表面胶水层。
2. **垃圾桶命名禁令**: 包名与主导出不得包含 `utils`、`util`、`helpers`、`helper`、`common`、`shared`、`misc`、`tools`、`stuff`。
3. **单一行为命题**: 包定位必须能凝练成一句不靠"以及 / 和 / `and`"硬拼的社区级行为描述。

| 维度         | 具象逐物反模式 (禁止)                                         | 行为本质正模式 (采纳)                                                                      |
| :----------- | :------------------------------------------------------------ | :----------------------------------------------------------------------------------------- |
| **终端交互** | `@iyowei/clis-prompt-utils` ("统一 sweep 和 codd 的问答工具") | `@iyowei/tty-prompt` ("支持非 TTY 管道降级与信号清理的极简终端问答原语")                   |
| **发行自证** | `@iyowei/clis-release-helpers` ("检查本仓构建和 npm 包")      | `@iyowei/npm-pack-verify` ("通过真实 `npm pack` 解包沙箱验证导出入口与最小运行时的校验器") |
| **参数解析** | `@iyowei/cli-shared-args` ("解析 update 和默认参数的工具")    | `@iyowei/argv-flags` ("零依赖的确定性短长旗标与位置参数解析器")                            |

### 闸门 3: 抽离净值与切割成本门槛

- **拒绝纳米包**: 剥离后的核心能力必须具备独立契约、非平凡边界条件与独立单测价值; 单纯包装一两个内置 API 且不足以摊薄建包与版本维护成本的小片段直接 `reject`。
- **低切割代价优先**: 检查 `cutCost` (内部相对依赖闭合数)。若把某段代码拎出来要同时拽出半个原包的私有状态与领域类型, 须先做接口参数反演解耦; 解耦后仍强粘连的应保留在原包内。

### 闸门 4: 社区可用性 & 依赖方向安全

- **零隐式全局态与可注入边界**: 凡涉及 `stdin` / `stdout` / `fs` / `env` / `spawn` 的包, 必须支持通过 options 或 adapter 注入替代实现 (默认回退标准宿主实现), 方便社区用户嵌入测试与上层框架。
- **架构拓扑约束**: 严禁库依赖 CLI, 严禁环依赖, 且保持浅层库依赖链 (遵循 [dependency-direction.md](../../../../docs/designs/dependency-direction.md) 公开库链深 `<= 2`)。

## 二、TS → Rust 转写友好型设计指引

鉴于本仓的「TS 原型验证 → 依据确定性转写契约转写成 Rust CLI」演进路线, 抽离出的共享包如果同时兼顾以下原则, 未来即可一对一映射成高质量 Rust crate:

1. **纯核与宿主 I/O 显式边界 (Functional Core, Imperative Shell)**:
   - 计算/解析/校验/规划逻辑一律做成纯函数 (`pure`), 仅接收不可变数据入参并返回确定性结构体或错误码, 不在其中直接调用 `process.exit`、`console.log` 或读写环境变量;
   - 必须访问文件系统/终端/子进程的包, 把边界动作收拢进小巧的 Trait 式回调接口, 让 Rust 端直接用 `std::fs` / `std::process` 对应实现。
2. **禁止动态运行时魔法**:
   - 禁用 `any`、运行时类型反射 (`Proxy` / `Reflect`)、动态 `import()` 与不透明弱类型字典 (`Record<string, unknown>` 混装异构状态);
   - 所有公共导出函数显式标注参数类型与返回值类型; 错误类型使用联合判别字面量 `code` (对应 Rust `enum ErrorCode`), 便于对接 [scripts/transcription/](../../../../scripts/transcription/) 契约测试集。
