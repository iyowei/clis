# 确定性三分法、9 大下沉模式与 ROI 标定规范

## 一、任务动作三分法 (Deterministic vs. Semantic Split)

审计任何 skill 时, 把指令拆到「单一动作原语」粒度, 按以下三类严格划分计算归属:

| 类别             | 判据特征                                                           | 归属决策                                                       | 典型示例                                                                                                                  |
| ---------------- | ------------------------------------------------------------------ | -------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| **A · 纯确定性** | 存在客观唯一答案, 规则可形式化为 AST / 图 / 正则 / 集合 / 数学公式 | **必须完全下沉脚本**, AI 不得肉眼重算或手工扫描                | 文件发现、AST 导出/调用链提取、重复代码克隆检测、死链/重号检查、JSON Schema 校验、快照备份与回滚、Mann-Whitney U 统计检验 |
| **B · 人机接力** | 「100% 召回候选与量化特征」确定, 「候选是否语义成立」需理解力      | **程序先扫后算, 吐浓缩 JSON; AI 只做语义裁决**, 末尾再过物理门 | 程序全仓扫出所有同名符号与文档命中行 → AI 筛选哪些文档真正受契约变更影响; 程序算出多包结构克隆簇 → AI 抽象本质行为命名    |
| **C · 纯语义**   | 依赖跨上下文意图理解、价值权衡、命名抽象或自然语言重构             | **坚定保留给 AI**, 禁止硬套脆弱启发式规则                      | 需求助产式澄清、架构重构方案构思、复杂 Bug 根因推演、融合更新设计文档                                                     |

## 二、9 大高发「AI 越权干苦力」模式清单

发现下列任意模式仍靠自然语言要求 AI 手工完成时, 直接列为重点改造对象:

1. **全仓多载体扫描**: 让 AI "逐个目录/逐类文件去搜调用点、测试、文档、配置", 必然随着上下文变长发生漏扫。应由脚本一次遍历并按载体分组吐出命中清单。
2. **AST 与依赖拓扑分析**: 让 AI 肉眼追踪 `import` / `export` 传递可达域、函数签名差异或兄弟实现同构性。应改用编译器 API / 词法扫描产出精确依赖图。
3. **文档引用与死链/编号审计**: 让 AI 检查 Markdown 相对链接是否失效、ADR 是否重号、示例代码能否跑通。这些是 100% 可静态判定的确定性图谱与编译检查。
4. **结构化格式与门禁自查**: 让 AI 在 Prompt 末尾 "自检是否包含必需字段、枚举取值是否合法、排版是否合规"。应全部替换为带非零退出码的 CLI 校验器。
5. **多轮状态机与台账维护**: 让 AI 靠记忆或手写更新 `state.json` 轮次、失败解封条件、防重复回退锁或收敛计数。应封装为 `begin-round` / `commit-round` / `rollback-round` 原子命令。
6. **物理备份与原子回滚**: 让 AI 手动执行拷贝改名备份或出错后手动复原多文件改动。应由脚本统一做检查点快照与无损还原。
7. **基准采样与统计学比较**: 让 AI 读两次耗时数字后 "凭感觉判断是否变快、是否超过噪声"。应由脚本执行 A/B 交替采样与非参数检验 (`p <= 0.05`)。
8. **清单计数与集合对齐**: 让 AI 核对 "N 个用例是否全部跑完、哪些未覆盖、总量是否等于明细之和"。计数与集合差运算永远交给程序。
9. **环境与平台拓扑探测**: 让 AI 运行一堆零散 `ls`/`cat`/`uname` 再拼凑系统态。应做成单条探测脚本直接输出标准事实 JSON。

## 三、ROI 止损分级 (`P0` / `P1` / `P2` / `SKIP`)

能写成脚本不代表**值得**写成脚本。每条改造建议必须同时过收益与维护成本两关:

| 级别                            | 触发条件                                                                                                                     | 建议动作                                                 |
| ------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------- |
| **`P0` (高危漏检必改)**         | AI 漏扫或算错会直接导致生产故障、破坏性漏改、假通过或污染主线 (如全仓变更影响分析漏掉调用方、状态回滚不原子、统计回归靠目测) | 立即立项脚本化, 并将旧的自然语言扫描步骤替换为调用新脚本 |
| **`P1` (高频降本提效)**         | 每次运行都需反复翻大量文件或跑多条命令拼装上下文, 脚本化后可一次压缩 70% 以上检索轮次与 token 消耗                           | 封装单入口 `prepare` / `scan` 脚本, 吐出浓缩 JSON 摘要   |
| **`P2` (顺手固化护栏)**         | 动作简单但人工偶有笔误 (如固定目录创建、命名规范检查、单文件模板生成)                                                        | 合并进现有脚本子命令或轻量独立 gate, 不另起复杂工程      |
| **`SKIP` (保持 AI / 放弃脚本)** | 满足任一否决条件: ① 极低频一次性任务; ② 判定高度依赖自然语言语义, 脚本只能写出高误报脆性正则; ③ 本身就是静态知识库文档       | **显式放弃脚本化**, 说明具体原因, 防止过度工程化         |

## 四、3 条反过度工程红线

1. **禁止写脆弱正则替代语义判断**: 比如用正则去猜一段自然语言文档 "是不是表达了架构妥协"。程序只采精确结构信号, 语义留给 AI。
2. **禁止把几万行原始日志全吐进上下文**: 如果脚本只是把全仓 grep 的 3000 行原文原封不动倒进 stdout 让 AI 看, 这不叫确定性工程, 这叫把上下文撑爆。脚本必须具备**聚类、去重、指标计算与优先级排序**能力。
3. **禁止无测试、无 Schema 的一次性黑盒脚本**: 凡新建核心确定性脚本, 必须配套输入输出契约或最小单元测试, 否则确定性工具坏了会集体静默假绿。
